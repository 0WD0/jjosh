#+title: 把项目归属变成引用身份
#+subtitle: 结构化 scope 提案；尚未实现
#+options: toc:2 num:nil

本提案讨论 jjosh 是否需要超出普通引用名约定的能力，不是当前命令手册。
当前可执行流程见 [[file:workflows.org][操作指南]]。下文的 typed scope、组件引用语法和 =--scope= 都是拟议接口。

子项目作为仓库开发单元的定义、目录归属、来源关系和本地身份，先由 [[file:subprojects-design.org][子项目模型]] 讨论。
本文只讨论引用 namespace；项目与 scope 可以关联，但不是同一个概念，也不要求项目模型与全部结构化引用改造同时落地。

* 要解决的歧义

当前 =main#engine@engine-upstream= 足以表达常见工作流，但底层仍是普通名字和全局 remote：

- 字面根名字 =main#engine= 与“engine 项目的 main”无法同时表达。
- 两个项目不能各自配置同名的 =upstream=，必须人为区分全局名字。
- parser、显示和同步边界对一个字符串承担不同解释，不能靠继续约定前缀获得可靠隔离。

结构化 scope 只解决这些身份与选择问题。
它不把 monorepo 拆成多个仓库，不按文件内容判定提交所有权，也不替用户隐藏 divergent change。
如果普通名字没有造成实际障碍，现有使用方式不需要先等待这项重构。

* 数据模型

#+begin_example
Scope          = Root | Named(name)
LocalRef       = (scope, kind, name)
RemoteRef      = (scope, kind, name, remote)
Connection     = (scope, remote)
kind           = bookmark | tag
#+end_example

scope 属于引用和连接配置，不属于 commit。
=main#engine= 仍可指向同时修改 engine、应用和构建文件的整合提交。
仓库保留唯一的 DAG、heads、workspaces、change ID 索引和 operation history。

View 按 scope 保存本地引用、远端观察和 tracking；引用目标继续使用完整 RefTarget，保留 adds/removes/absence。
远端观察可以在没有可用连接配置时存在，例如从 native bundle 导入的状态。
不得把冲突目标压成一个 OID，也不得要求“每个 scope 的每个 change 只有一个版本”。

项目挂载、filter、来源 base 是转换配置，不是引用身份。
移动目录、修改 filter、scope rename 和 remote rename 是四种不同操作。
本提案不附带任意历史布局搬迁，也不引入跨仓库项目 UUID。子项目模型中的仓库本地 ProjectId 用于元数据关联，不是这里的引用 scope 或另一套 change 身份。

* 用户如何选择

推荐显示形式仍为 =name[#scope][@remote]=，但 parser 和 formatter 必须按组件工作：

| revset 收到的文本 | 拟议含义 |
|------------------+----------|
| =main= | 根本地引用 |
| =main@origin= | 根 origin 的观察 |
| =main#engine= | engine 的本地引用 |
| =main#engine@origin= | engine 的 origin 观察 |
| ="main#engine"= | 根中名字恰为 main#engine 的引用 |
| ="feature#parser"#engine= | engine 中名字恰为 feature#parser 的引用 |

表中的引号属于 revset 语法；shell 引用是另一层。不能通过 split 显示文本恢复身份。
显式 scope 的引用解析失败就报错，不退回全局 commit/change ID。
=@= 仍是工作副本，不新增按项目的工作副本 ID。

命令选择遵守以下契约：

- 精确名字省略 scope 时属于根；显式 =--scope engine= 才把该命令的未限定名字放入 engine。
- 命令 scope 与参数中的显式 scope 冲突时拒绝，不让任一方静默覆盖另一方。
- 修改或删除的名字模式限于所选 scope；跨 scope 批量修改必须显式选择范围。
- 浏览集合默认保持全局。=bookmarks()=、tag 集合、日志、不可变历史和维护遍历不能漏掉子项目；组件过滤可显式缩小范围。
- 模板、排序、去重、补全和 operation diff 使用完整身份。全局 trunk 策略不从多个项目的 main 中猜一个。

拟议的单项目传输以 =git fetch/push --scope engine --remote origin= 选择范围。
=--remote= 和 =--all-remotes= 只在该 scope 内匹配；没有 =--scope= 时操作根。
默认选择依次使用显式参数、scope 配置和该范围内的 jj 默认规则，命名 scope 不隐式继承根发布路由。
当前按 =#PROJECT= 自动分发的批量发布若迁入新模型，必须显式定义跨 scope 选择，不能按提交修改了哪些目录分发。

* 版本不是名字的附属品

change ID 联系一个 change 的不同版本，commit ID 标识具体版本；scope 不改变这个关系。
两个 remote 可以各自指向同一 change 的不同版本，也可以出现本地引用冲突。这是两种不同状态。
裸 change ID 的歧义处理保持 jj 现状，精确引用或 commit ID 用于选择版本。

设 C 同时修改项目 A、B，发布 A 得到 P，重新获取后得到 C'：

- C' 与 C 的 change ID 相同，不足以证明整份提交等价。
- A 子树相同，也不能证明 B 的修改已经发布或可以被替换。
- 有明确且有效的转换边界时可以复用已知 canonical 版本；否则保留合法的多个版本。
- 验收应检查未发布工作与父图是否正确，不能把“没有 divergence”本身作为目标。

native 导入要继续保留原生版本、空提交、有序父边、冲突树和引用冲突。
Josh 过滤可以裁剪提交、调整父关系，历史中的 workspace/stored 定义还可能改变过滤语义；它不能冒充无损 native 导入。
不带有效 change-id 头的 Git 提交依赖 OID 生成身份，改变 OID 不自动保留原生 change 身份。

* 从版本到传输

引用选择、历史转换和发布授权是三层输入，必须分别表示：

| 输入 | 作用 | 不能代替什么 |
|------+------|--------------|
| 用户选定的 canonical 版本与引用动作 | 决定发布内容 | 来源上下文 |
| 具体 raw 历史、filter、base 与接续信息 | 重建来源坐标 | 目标当前位置 |
| 实际 endpoint、完整 ref 与 expected-old | 校验覆盖授权 | 转换结果正确性 |

** 获取

传输先接收明确选择的 raw refs 和对象，转换具体版本，再把结构化引用更新交给 jj tracking 合并。
删除推断只覆盖本次完整观察的 scope、remote、kind 和名字范围；未请求或获取失败不等于远端删除。

转换产生同 change ID 的新版本，并不能直接授权 synthetic rewrite 替换旧整合版本。
必须在进入引用合并前判定转换边界；不能将现有 raw Git 的新旧可达集合推断原封不动套到坐标变化上。

根 Git scanner 的实际扫描集与已知观察候选集都要排除 scoped 私有状态，否则会把没扫描到的 scoped refs 当成删除。
导入的 scoped =@git= 是来源观察，不得驱动当前 backend 的根分支。

** 发布

对已有目标，逆转换必须保留目标过滤范围外的内容并使用正确的 raw 父图。
对新目标，来源基线必须能由选定历史确定；存在歧义就要求选择具体版本，不能按 change ID 挑第一个候选。
没有项目内变化时不应把远端退回一个较旧的等价投影版本。

lease 按实际 endpoint 和完整 ref 记录 raw 身份。upstream 的 base、另一个 fork 的观察、刚收到的 advertisement 都不能授权覆盖当前目标。
annotated tag 同时需要直接对象 ID 和 peeled commit；只比较后者会漏掉 annotation-only 更新。改变签名对象的目标不能继续宣称签名有效。

每个更新只有在收到明确成功结果后才能推进观察。多个逻辑 remote 指向同一个实际 ref 时，在准备阶段拒绝重复目的地。
一个 remote 的多个 push URL 若不能逐 endpoint 转换、检查和记账，就必须明确拒绝，不能只处理第一个。
这不提供跨 remote 的原子发布，也不允许 operation restore 撤销外部结果。

* 配置与对象各归其位

Git config 是 URL、push URL、认证相关设置与 per-remote 选项的权威来源；转换文件只保存转换语义。
连接仍通过 named remote 配置解析，保留 include/global 来源边界和未知配置项，不把它们展平写回本地。
独立 projection 继续连接真实来源 endpoint，不引入本地 transport façade，也不因为配置了 filter 就自动获得项目 scope。

Git 的 remote section 是扁平的。建议用稳定的内部 handle 对应 =(scope, remote)=，以显式 metadata 声明所有权：
逻辑改名保持 handle 不变，创建前检查有效配置中是否碰撞，不能通过名字前缀接管用户 section。
这是局部存储键，不是项目身份；代价是原生 Git 的 remote list 会看到内部 handle。

来源对象、浅边界和不可重建的转换对应关系由 backend/转换层保管。
当前按 endpoint 隔离来源的做法应继续成立：完整和浅获取走同一流程，canonical 图保持闭合，不能把来源浅状态变成 monorepo 的全局 shallow。
保活不要求把 raw commits 暴露为用户 heads；但可见文件与 canonical 对象也不足以恢复所有逆转换输入。
可重算的缓存不能成为引用存在的前提，不可重建的 provenance 则不能被当成缓存随手删除。

* 如何迁移而不重新解释历史

这不是给 View 加字段后就能完成的改动。切换需要覆盖：

1. typed symbols、View 编码、全局遍历和引用合并；所有冲突项与 tracking 状态保持完整。
2. parser/formatter、revset、模板、补全、命令范围和默认策略。
3. Git 配置所有权、物理 refs 隔离、转换更新接口、逐 endpoint 发布记账。
4. operation restore、native bundle 编码、能力标记与旧 writer 排除。
5. 显式归属迁移和中断恢复；确认新状态成立后移除旧物理映射路径。

旧 operation 的名字按字面根名字解码，不拿当前项目目录或配置重新解释旧历史。
迁移计划要明确每个旧引用、观察、remote、默认项和 private ref 去向；有歧义时要求映射。
迁移不重写提交图、不合并 divergence、不激活导入的连接，也不刷新发布 lease。

Git config、物理 refs 和 jj operation 不是一个原子存储。
恢复协议必须覆盖中断、重复执行、锁冲突和并发 operation heads；不能用“一次 jj transaction”代替跨存储恢复。
旧格式不得在不认识 scope 的程序中被静默写回。

* 实现是否成立，看这些结果

- 根字面 =main#engine= 与 scoped main 共存，显示再解析无损；两个项目各自的 origin 可独立改名和删除。
- 全局日志、不可变历史、rebase、索引和 GC 不漏掉任何 scope；同 change 多版本与引用冲突各自保留。
- 获取部分 refs 不删除未选择观察，根 Git import/export 不复活或清空 scoped 私有状态。
- 部分项目往返保留其他项目的未发布工作；相同 change ID 不触发未经证明的整体替换。
- fork 的过滤范围外内容不丢失；stale lease、annotation-only 更新和重复目的地都被正确处理。
- native import/bundle/operation restore 保留冲突、divergence 和 tracking；恢复本地状态不撤销远端发布。
- 浅边界变化不导致 canonical 图缺父，也不丢失旧本地版本需要的逆转换依据。
- 迁移在歧义、中断和旧 writer 面前明确停下，恢复后旧物理 refs 不再作为根引用出现。

这些是未来实现的验收条件，不是已通过的测试报告。
