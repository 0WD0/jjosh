 #+title: jj 原生当前状态整合设计
#+date: 2026-09-10

* 结论与本轮边界

目标是把多个来源的当前 jj 状态整合为一个可继续工作的 jj 仓库，不是先导出 Git DAG 再重建 jj 信息。

按用户后续决定，旧 operation 历史和旧演化信息均不在本轮范围内。目标从一次明确的导入操作开始记录新的 operation 和演化。原仓库保持不变，作为回退与查证依据；不为这两项设计历史归档、跨库 evolog 或新的 GC 根机制。

保留 change ID 不等于保留整个 change 的演化史。同一 change ID 的多个当前可见版本属于当前状态，必须保留；已经隐藏、且只通过旧演化或旧 operation 可达的版本不因此进入导入闭包。

本轮成果是设计与隔离实验，不是生产迁移工具，也未重新启动真实迁移。

* 保真契约

| 对象 | 处理方式 |
|------+----------|
| 当前 view 的可见 heads | 保留全部，不只取 @ 或有书签的分支 |
| 提交父关系 | 映射父 ID，保留顺序、合并、独立根和侧支；不串行重放各项目 |
| 当前提交的 change ID | 保留；不因 divergence 分配新身份或自动 converge |
| 原生提交内容 | 映射每个带符号树项；保留作者、描述、时间等约定字段及冲突标签 |
| 书签、tag、remote target | 映射全部引用项，包括冲突的增加/删除项与 absence；命名空间显式划分 |
| remote tracking 状态 | 保留到对应的来源作用域；引用别名与外部远端分支名不能混淆 |
| 当前 workspace | 捕获实际已批准文件内容；原 workspace 选定提交可保留为有角色的引用，不伪造已挂载的目标 workspace |
| Git HEAD、index、已观察 Git refs | 是具体后端的工作状态，不直接套到目标后端；有独立 Git 历史时明确保留其输入头 |
| 旧 operation、旧 predecessor 历史 | 不导入；旧 legacy predecessor 指针不能留成指向缺失对象的悬空引用 |
| 新操作和新演化 | 由目标正常 jj 事务产生 |

所有“保留”都以已选定的一致来源状态为准。源有尚未导入 jj 的 Git checkout、引用变化或未快照工作时，不能直接把存储的 @ 当成完整输入。

原始 Git 对象字节、任意 Git 扩展头和原提交签名的逐字保留，不等价于 jj 原生字段保真。路径或父 ID 改变后，不可冒用旧签名。实现必须提前说明签名与编码边界，记录原对象对应关系，并检查后端实际返回的提交字段；实验只覆盖未签名输入。

* 为什么不再从总基线重放

旧尝试先制造“包含所有来源”的干净组合基线，再把已有本地提交相对它重放。这会改变原历史的基底解释。例如独立 Git 根在 jj 中以 root() 为父；把它接到已含来源代码的基线，会把整棵源树当作相对空树的增加，产生并非原工作已有的冲突。

新的整合顺序是：

1. 保持各来源的当前原生父图与原生树语义。
2. 对整个所需闭包进行路径布局映射。
3. 导入 namespaced 当前 view。
4. 用普通 jj 多父提交组合选定来源头。
5. 在新的整合修改中处理构建接线、配置整理、子模块展开和共享依赖的明确协调。

整合提交不是来源的上游基线，不能设置成会冻结全部本地祖先的 jjosh/trunk。

原提交内部的历史目录变迁不必提前抹平。例如 Appkit 的旧版本可以仍叫 parley.el，当前版本叫 chidu.el。先做整个 Appkit 根的重定位，而不是把历史两种名称强行归一化。

* 输入获取与闭包

** 一致来源输入

建议在隔离来源副本中完成必要的 native snapshot / Git 状态协调，读取来源原生 Store 与 view，不在真实来源上自动改写或合并操作。

- 捕获前记录来源身份、当前选择状态与实际工作区范围。
- 保留原 jj 状态头与需要保留的 Git-only 头，避免协调 checkout 时丢掉其中一支。
- 快照仅覆盖批准的源码和配置范围，不读取工作区外运行态、凭据或密钥。
- 有稀疏工作区时遵守原稀疏范围，不把未物化路径当成删除。
- 发现来源在捕获期间变化时拒绝采用该快照；不冻结桌面，也不声称跨所有仓库取得了文件系统原子快照。
- 浅克隆/部分克隆必须明确边界。需要补全时在隔离副本中补全、重载和重新索引后再选定输入，不把截断点偷偷当作真正根。

这部分尚未在真实多仓库并发编辑环境验证。

** 当前状态的对象闭包

入口不是所有 refs/jj/keep，也不是每个旧 operation 的 view。

入口为当前选定 view 中全部被引用的提交：heads、local/remote refs 的全部原生项、workspace 选择，以及记录的 Git 引用。然后取其父祖先闭包。额外保留的 Git-only 头由输入计划明确列出。

当前 view 中隐藏的引用目标可以只索引而不变成可见 head。不能因为搬运了一个对象就把它重新公开成活动分支。

旧演化闭包不遍历，旧 operation 不复制。导入操作不伪造旧操作的时间、内容或因果关系。

* 原生映射与发布

** 身份域

至少区分以下概念：

- OriginId：这份原生输入的来源身份，不依赖它当前的磁盘路径。
- ComponentId：逻辑源码归属。明确共享的依赖可以有多个输入来源，但只有一个目标归属。
- LayoutId：确定的路径布局变换。
- 原 native commit ID 与目标 mapped commit ID。
- Raw upstream pin：外部来源仓库中的原始提交，不能用 mapped ID 替代。

映射键必须包含来源与布局上下文，不能只用 Git OID 或 Commit 对象做跨 Store 的键。jj 的 Commit 比较只看 ID；不同 Store 的补充元数据可能不同。

change ID 本身不重命名；重复 change ID 不足以证明两个版本可以合并或吸收。若映射造成可见 divergence，应说明其来源，而非消除标记。

** 树与提交

布局变换作用于每个原生树项，不经过 Josh 的提交历史裁剪器，也不调用普通 rewrite_commit 来冒充一次用户编辑。

- 空树仍映射为空树。
- 保留冲突项的正负位置和标签。
- 单一来源内必须验证路径映射无损；碰撞检查覆盖同一逻辑冲突树的全部项。
- 保留父顺序、空提交和 merge-own delta 所对应的原始状态；不按“过滤后变空”剪枝。
- 历史子模块 gitlink 可先作为原生树值保留；最终展开属于明确的整合修改，不虚构过去已经展开。
- 默认保留源原生作者、描述、change ID 等字段。调用 Store::write_commit 后验证实际返回数据，不能忽略后端碰撞处理造成的时间修改。

当前公开 API 已经可用于这个范围：

- Store / backend 读取原生 Commit 与每个树项。
- Store::write_commit 写入明确构造的 native Commit。
- MutableRepo::index_commits 加入索引而不自动公开所有对象。
- MutableRepo::set_view 设置经过映射、验证的当前 view。
- Transaction::commit 发布目标自己的导入操作。

研究原型直接使用了这些接口，没有为当前状态导入新增 jj 核心接口。

** 当前 view 与工作区

local ref 名、remote 名及其 ref 名必须协同映射，保留 tracking 对应关系。外部 raw 分支名另外保留在来源绑定中，不能把 a/main 当作外部仓库也存在的分支。

各源当前 view 的组合必须是显式且经命名空间检查的组合，不通过“把独立 operation 当成并发操作”来让 jj 猜测结果。

目标只建立真实的新 workspace。源 workspace 的选择可先保留为来源角色引用，例如 a/workspace/default；不会仅复制 wc_commit_ids 就声称这些工作区已被挂载。

建议目标使用非 colocated 的 SHA-1 Git backend：

#+begin_src sh
jjosh git init --no-colocate workbench
#+end_src

这不是“原生”的定义或必要条件，只是避免普通 Git HEAD/index 自动同步干扰原生状态整合。实验确认普通 jj 编辑和冲突书签在该模式下可以继续工作。需要 Git-only 工具时，须明确兼容入口，而非让它们误把整个组合仓库当作单个来源。

来源 remote observations 与可执行 fetch/push 绑定是两件事。导入不能自动启用目标远端；后续传输必须通过来源绑定维护正确的作用域映射。直接运行不知作用域的 Git import/fetch 不在该绑定的保真承诺内。

* 组合与来源同步

** 组合入口

选定主工作头后，可以使用现成命令：

#+begin_src sh
jjosh new a/workspace/default b/workspace/default -m 'Integrate native source states'
#+end_src

它新建一个整合提交，不把 A、B 旧提交变成彼此的串行依赖。未选入这个工作树的侧支仍保留在 view 中。

Appkit 作为整个原生来源导入，保留内部 sibling 布局。jjosh 整体的跨目录修改也只导入一次；布局可以分别映射 jj、josh 和其余源码到 src/jj、src/josh、src/jjosh，而不是先分别导出三份本地 patch 栈。

Cargo 相对路径、个人配置与 Guix 入口等调整，应记录为新的整合修改。保留旧源码状态不等于承诺每个历史版本在新物理布局中无需环境调整就能构建。

** 共享依赖与子模块

共享 moonlight-common-c / msquic 必须由明确的 ComponentId 统一归属，不能用 Josh overlay 覆盖两份来源，也不能仅凭当前树相同就删除一支历史。

对于明确属于同一组件的两个输入，可以在同一目标路径上用原生 merge 协调其来源头；内容不同就保留冲突并明确解决。最终只有一个权威目录，两个输入的当前历史仍有可追溯的父关系。

单消费者依赖可在原嵌套位置展开。最终整合提交要实际替换 gitlink 为 tracked files，并更新已失效的 .gitmodules、构建路径和维护入口；不是仅放一个 marker。旧历史保持原状。

** 来源绑定而非全局 trunk

目前 link.rs / link_refs.rs 的核心假设是一个全局干净组合基线：

- existing_baseline 查询单个 jjosh/trunk。
- publish 会删除未列入本次结果的 jjosh/source/*。
- update 重建 clean_composition 后重放后代。
- 默认 immutable 策略包含 link_trunk()。

因此，把多个已含本地修改的来源头 merge 后写进 jjosh/trunk，既可能冻结本地历史，也会使后续更新错误解释它们。需要改的是这层来源管理模型，而非首先再发明提交重放算法。

来源绑定需明确记录：组件/来源身份、原始 remote 与分支、可信 raw pin、原生锚点对应、来源坐标中的投影、目标布局映射、所属组合及发布目标。

.link.josh 的 filter 是有坐标系的：其输出映射要与布局组合；raw pin、raw 发布 lease 和外部 URL 不跟着目标 commit ID 改写。推荐在执行层分开“存储的来源 metadata”和“编译后的目标投影”，而不是为了搬目录就重写所有历史 marker。

单一来源更新只修改自己的绑定、pin 与相关状态，不清掉其他组合的 source refs。来源基线与当前整合头必须是不同角色。

** 已知 pin 的来源推进

数据导入与判定上游基线是两个独立问题：完整导入原生状态不需要先给整个仓库找一个总 upstream base；安全启用来源同步则必须逐源确认 pin。

当历史没有把来源 pin 表达为当前提交的祖先时，可以研究以可信 pin 为显式三方基底的来源推进，而非倒过来改写旧 parent：

#+begin_example
结果树 = merge(当前本地状态, 已记录的来源 pin, 新来源状态)
新提交父边 = [原本地头, 新来源头]
#+end_example

这是新的、有明确来源依据的 merge-own delta，不是强制选择某个冲突侧。它不把旧本地根冒充上游，也不宣称来源关系过去就是 commit parent。

隔离实验已验证：普通祖先推断合并会复活已删除的测试文件并产生代码冲突；以正确记录的 pin 做三方合并，则保留本地删除、引入上游新代码、保留其他本地文件，并保留原两条父边。

这只验证了原生树运算与提交表达能力。完整 link update/push 的绑定查找、历史投影对应、上游 FF 校验、lease 和受影响分支策略仍需独立实现与验证。pin 不可信或不唯一时不能套用此运算。

* 原型实验与证据

所有输入都是 /tmp 下创建的小仓库；真实来源未修改，也未远端推送。

| 场景 | 观察结果 |
|------+----------|
| 当前原生状态导入 | A、B 各导入 4 个所需提交，包含独立根与多父合并 |
| native payload | 原型逐个检查映射后的 change ID、父列表、作者、时间、描述及原生树/标签字段 |
| 原 operation / evolution | 目标只有自身初始化与导入操作；已知旧演化版本未进入映射 |
| 原生组合 | 普通 jj new 得到 a/file、a/side、b/file；A 没有新增冲突 |
| 文件冲突 | B 原有两侧内容与 2-sided conflict 保留 |
| 引用冲突 | b/choice 的原生冲突目标保留，普通 jj new 后不消失 |
| 合法 divergence | 同一个 change ID 的两个当前可见版本均保留 |
| 继续工作 | 解决 B 冲突后编辑 A 的已导入祖先，整合 change ID 不变，解决结果仍保留 |
| 新演化 | 导入后的修改产生正常的新 evolog 关系，不依赖旧演化导入 |
| GC | 普通 jj util gc 后当前文件与冲突书签仍保留 |
| 来源推进 | 显式可信 pin 的三方合并保留删除、得到上游新代码且无该人工冲突 |

原型使用预复制的本地 Git 对象作运输，但从来源 native Store 读取身份和状态，不通过 Git refs 重建 jj 语义。它只是小样本研究程序：不处理实际网络、真实多源并发捕获、签名输入、任意引用命名或完整来源管理，不应当作为生产导入脚本运行。其简单拓扑扫描也不是生产性能实现。

* 实现顺序与边界

1. 实现只读来源盘点与确定的导入计划：范围、角色、布局、命名空间、对象闭包、输入稳定性、签名/浅克隆边界。
2. 基于现有 jj-lib 接口实现当前状态导入协调器，在全新目标 staging repo 中构造与验证对象及 view；不扩展旧 operation/evolution。
3. 普通 native merge 建立工作入口；把配置接线、共享依赖协调与 gitlink 展开记录为明确的新修改。
4. 将 jjosh 来源管理从单全局 trunk 改为有作用域的绑定；验证真实来源更新和各自反向导出，保留现有发布保护。
5. 实仓验收通过后才采用目标目录；原来源和之前 workbench 演练均不被覆盖。

默认不把现有 projection transplant 作为主迁移路径，也不继续为其补齐历史归档能力。

本轮没有证明已经需要新的 jj 核心存储层、operation federation 或完整历史导入 API。当前状态导入的原生表达与基本可操作性已经能用现有 API 验证；实际缺口主要在 jjosh 的来源作用域、输入捕获、投影坐标与发布协调。
