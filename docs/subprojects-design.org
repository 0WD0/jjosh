#+title: jjosh 的项目模型
#+options: toc:2 num:nil

jjosh 在一份 jj 仓库中组织多个开发项目，并在这份仓库与各项目的外部仓库之间转换历史。
本文从内容和历史的关系出发，说明项目、引用、来源映射及状态保存方式。具体命令见 [[file:workflows.org][使用指南]]。

* 一份完整历史，多个交付对象

设一个仓库同时包含应用与 parser：

#+begin_example
apps/app/
libs/parser/
build/
#+end_example

一次接口修改可以同时涉及 =apps/app/= 和 =libs/parser/=。jj 将它记录为一个 change 的版本，提交树包含整个仓库，父边连接完整的开发历史。
开发者可以将修改保留在一起，也可以用 rebase、squash 等操作重新组织它们。

项目为这张修改图提供交付边界。将 parser 定义为 =libs/parser/= 后，任一完整提交都可以作为 parser 的发布终点；转换时从该版本取出项目内容，并处理有关的祖先历史。
因此，“提交修改了哪些项目”和“这次选择发布哪个项目”是两个独立问题。

DAG、change ID 索引和 workspace 都属于 jj 仓库。项目保存内容范围及交付关系，所有项目共享同一套修改操作。
构建脚本等公共内容可以继续作为普通仓库文件存在。

* 内容的位置

项目记录包含显示名和完整提交树中的目录：

#+begin_example
ProjectRecord {
  name: "parser",
  canonical_root: "libs/parser"
}
#+end_example

这里的 canonical_root 称为 *完整树路径*。项目名指向开发对象，完整树路径决定它在提交中的内容范围。

每个活动项目占用一个非根目录。目录之间互不重叠，既不能相等，也不能互相包含。
目录可以暂时没有文件；例如项目已登记、来源历史尚未获取。
登记检查已记录树中的路径，已有普通文件或 symlink 占用该位置时会报错。

工作副本是完整树的一种检出方式。通过 sparse 映射，某个 workspace 可以把 =libs/parser/= 放到磁盘根目录，另一个 workspace 则检出完整布局。
这两种工作方式记录的仍是同一个完整树路径。
命令中的项目路径先按 cwd 和 workspace 映射解析，再保存到项目定义中。

登记项目产生一个 jj operation，记录的是定义变化。文件快照、检出和源码提交由相应的 jj 操作完成。

* 外部仓库怎样表示一个项目

同一个 parser 可以出现在几种不同布局中：

| 仓库 | parser 的位置 | 来源表示 |
|------+---------------+----------|
| 上游组件库 | src/parser | =JoshFilter(":/src/parser")= |
| 上游的同布局 fork | src/parser | 同一个 filter 值 |
| 独立发布仓库 | 根目录 | =Whole= |
| 按 workspace.josh 组织的仓库 | 随版本定义 | =JoshView(PATH)= |

本地始终使用 =libs/parser/=。每条外部关系分别描述自己的来源表示，因而一个项目可以从不同布局获取，也可以向不同布局发布。

来源表示的求值结果以项目根为坐标，随后放入本地完整树路径。若用 F 表示来源转换、L 表示本地目录放置，获取的内容映射可写为 =L ∘ F=。

发布则从本地版本中选择项目内容，结合来源上下文重建外部历史。
例如向上游组件库发布时，需要保留 =src/parser/= 之外的上游内容。filter 可能丢弃过信息，这些信息来自保留的来源对象和转换对应关系，而不是仅从本地项目树推算。

** 绑定

一条来源关系用不可变绑定表示：

#+begin_example
BindingRecord {
  target,
  connection_id,
  representation,
  base
}

target         = Project(ProjectId) | RepositoryView
representation = Whole | JoshFilter(String) | JoshView(String)
#+end_example

project 绑定的 target 指向项目，base 指定可选的来源上下文选择规则。
绑定一经创建，其含义保持固定。使用另一种表示时创建新绑定，让已有历史继续引用原来的转换含义。

=--like= 将已有绑定的 target、representation 和 base 值用于新绑定。
新连接有自己的地址、权限、获取记录和发布状态；相同表示只是两条关系采用相同的转换规则。

RepositoryView 将转换结果用作整个仓库的历史，适用于独立过滤仓库。
它直接使用根布局和普通引用名字；project 绑定还负责把转换结果放入项目目录。

** whole 与原生状态

Whole 表示整个来源属于这个项目。输入来自本地 jj 仓库时，可以携带原生 change 身份、有序父边、空提交、divergence 和冲突。
重新放置目录会改变 commit ID，change ID 则用于保留开发身份；失效的提交签名会移除并报告。

Josh filter/view 按过滤规则转换历史，可能裁掉内容和提交。导出也可以裁掉仅影响其他项目的提交。
导入保真与交付裁剪分别服务于开发状态保存和项目历史输出。
当前历史转换使用 SHA-1 Git backend，gitlink 作为引用保存。

* 引用怎样选择交付对象

项目登记时建立一个引用 label。例如 label =parser= 关联到 parser 的 ProjectId：

#+begin_example
topic                            仓库中的普通书签
topic#parser                     parser 的交付书签
topic#parser@origin              parser 的 origin 上 topic 的本地记录
#+end_example

本地书签始终指向完整提交。=#parser= 给发布选择提供项目身份，wire ref 则使用去掉项目 label 后的 =topic=。
bookmark 和 tag 使用相同的项目选择规则。

label 在 operation 状态中保存，项目显示名可以独立修改。因此将 parser 改名为 syntax 后，原来的 =topic#parser= 仍然有效。

名字的解释由登记状态决定。没有登记的 =#后缀= 是字面名字；登记时会检查已有本地引用和远端记录，避免改变它们的解释。
同样，普通来源或 RepositoryView 的 raw ref 若占用一个已登记 label，会在写入前被拒绝。项目来源通过自己的绑定完成命名和目录映射。

远端引用记录与本地书签之间的更新关系由 tracking 管理。fetch 接收来源版本，tracking 合并引用更新，new 等命令选择工作头。

remote 命名空间已按根／ProjectId 隔离，每个项目都可以使用 origin。本地引用仍通过已登记的 label 解释普通名字；将本地引用改为完整 typed identity、允许根字面名字与项目引用无歧义共存，见 [[file:scoped-references-design.org][引用 scope 提案]]。项目路径和 label 的整体迁移是另一项契约。

* 稳定身份与本地连接

对象用稳定 ID 标识，名字供人选择：

| ID | 标识的对象 | 生命周期 |
|----+------------+----------|
| ProjectId | 开发项目 | 显示名变化时保留 |
| BindingId | 不可变来源关系 | 新关系使用新 ID |
| ConnectionId | 本地 remote 连接实例 | rename 保留，remove 后重建使用新 ID |

这些 ID 的作用域是当前仓库。相同名字或 URL 不会自动建立跨仓库身份对应。

remote 的 URL、push URL 和认证属于本地连接配置。一个连接实例最多关联一个活动绑定；多个项目使用同一外部仓库时，各自配置连接，逻辑别名可以相同。逻辑身份由根或 ProjectId 与项目内名字组成，不依赖前缀；Git config 和物理 refs 使用独立的内部 handle，名字改动不改变 handle。
set-url 调整连接地址，绑定仍保留原来的项目和表示。

ConnectionId 使操作恢复能够区分“原来的 origin”和“删除后重新创建的 origin”。
恢复出的绑定仍关联原连接实例；连接已不存在时显示为未连接，开发者可显式处理旧绑定和远端记录。
若删除后同名重建，再恢复旧 remote-tracking 状态，旧名字和记录不会自动归给新连接。清理断开的旧观察后，可用 =project resolve --connection ID --name NAME= 为当前绑定的实际连接明确修复名字；系统校验连接与项目归属，不按同名或唯一候选猜测。

地址也有自己的身份。来源对象、浅边界和发布 lease 按实际 endpoint 定位；同一个连接可以先后访问不同地址，不同连接也可能访问同一个地址。

默认目的地是本地连接选择的一部分：=git.projects.LABEL.fetch= 与 =git.projects.LABEL.push= 支持 remote 名字、显式模式和列表，值只在该项目内解析。push 的选择必须解析为单一目的连接；fetch 可以展开多个连接。两者均不继承根的 =git.fetch=／=git.push=。
配置按稳定的引用 label 定位项目，项目改显示名时仍然有效。仓库内的配置随 remote rename/remove 更新，用户级配置独立维护。

* 一次获取留下什么

获取既产生可供本地开发使用的提交，也记录这些提交怎样从外部历史转换而来。

=git fetch --project parser --project app= 选择多个项目，重复项目去重；=--all-projects= 选择全部未删除的登记项目，两者互斥且都排除根。不带项目选择时只获取根。
每个项目独立解析显式 =--remote= 表达式，其次采用 =git.projects.LABEL.fetch=，否则选择唯一连接或项目内的 origin；=--all-remotes= 展开每个所选范围的全部连接。
整批范围、配置和绑定在网络请求前预检。缺少显式别名、没有活动连接或未解决定义都会报错，不会跳过离线项目；=--all-projects= 包含冲突候选而不是只挑健康定义。=--revision=／=--fetch-url= 要求去重后只有一个物理 remote。
预检完成不等于所有服务器可达；网络阶段可能部分失败，获取也不会自动决定整合策略。

以过滤上游 =src/parser/= 为例：

1. 按 remote 和选择条件接收外部 ref 及对象。
2. 使用绑定的表示转换历史，生成位于 =libs/parser/= 的本地版本。
3. 安装对应的本地 mirror，更新远端引用记录及转换观察。
4. 根据 tracking 更新本地引用，保存此次 operation。

引用 target 描述本地版本，ConversionObservation 保存来源依据：

| 字段 | 用途 |
|------+------|
| binding_id、binding | 确定转换所用的不可变定义 |
| connection_id、endpoint | 确定被观察的连接实例与实际地址 |
| raw_ref | 来源完整 ref 名 |
| terms | 带符号的 canonical/raw 对象对应项 |
| base | 实际采用的来源上下文 |
| generation | 历史 normalization 所属代际 |

观察按 remote、name 和 kind 保存；kind 区分 bookmark、tag 和直接获取的 revision。
一次性导出中，执行转换的来源绑定与被观察的发布目标可以属于不同连接。

** 相同内容与不同来源

上游只修改 parser 之外的文件时，新的 raw commit 可能仍映射到同一个本地 commit。
本地引用位置可以保持不变，来源观察仍需更新；后续反向发布要保留上游刚修改的外围内容。

因此，引用 target 和转换依据分别保存、分别合并。
两个 target 可以收敛为一个 commit，而相关 endpoint、raw 对象或 generation 仍可能需要保留多个候选。
恢复历史观察时使用其中记录的来源依据，当前 URL 和 filter 配置不能替代它们。

浅获取还会影响祖先关系。增加深度可能生成新的 normalization generation，已有观察继续引用其原来的代际。

* 一次发布怎样确定

发布计划将三个选择放在一起：

- *交付对象*：本地引用、项目和所选完整提交。
- *转换依据*：来源绑定、表示、raw 上下文及相关代际。
- *写入目标*：实际发布地址、完整 wire ref 和预期旧对象 ID。

目的 remote 有匹配绑定时，使用它自己的表示。向未绑定目的地导出时，用 =--source= 明确选择来源关系。
每个所选引用分别解析目的地。项目引用优先采用显式 =--remote=，其次按稳定 label 读取 =git.projects.LABEL.push=；没有配置则选择项目唯一连接或项目内的 origin，否则报告歧义。未知或跨项目的默认值报错，不回退到根。
普通根引用采用根的 =git.push= 和默认规则；项目引用不继承它。=--remote fork= 在每个引用的项目内解析，=--remote origin#= 才明确选择根的 origin。
=git push --bookmark 'glob:topic#*'= 按各引用的 label 批量路由；加 =--remote fork= 要求每个被选项目都有自己的 fork。选择不取决于提交改了哪些目录。

转换和传输预检完成后，计划中的 expected-old 就是提交给目标服务器的精确旧 Git 对象 ID。
已知目标状态保存在 endpoint/ref 的 lease 中。这个状态独立于本地 canonical commit：即使两个 fork 转换出相同版本，它们仍有各自的更新依据。
annotated tag 的 lease 使用 tag 对象本身的 ID，从而覆盖只改变注释的更新。

所有选中项先完成选择、转换、可发布性检查和 endpoint/ref 碰撞检查，再开始写入远端；任一项目缺少显式别名会阻止整批发布。
dry-run 展示这一份已准备计划，包括新 raw target。网络发布可能部分成功，不提供跨远端原子性；系统只为独立确认的结果更新本地发布记录，op restore 也不能撤销外部结果。

项目绑定只描述转换。push 使用配置的 push URL，未配置时使用普通 URL；服务器负责访问授权。原生 Git 直接访问外部仓库时不会经过项目转换。

* 操作历史与恢复

状态按用途保存在不同位置：

| 状态 | 保存位置 | 恢复方式 |
|------+----------+----------|
| 项目、绑定、label、本地引用 | operation View | op restore 的 repo 部分 |
| 远端引用、tracking、连接归属、转换观察 | operation View | op restore 的 remote-tracking 部分 |
| 地址、认证、连接实例配置 | 本地 Git config | 本地连接管理 |
| 项目默认获取／发布 remote | 本地 jj 配置 | config 与 remote 生命周期管理 |
| 来源对象、normalization、转换对应关系、发布 lease | backend 与来源存储 | 按历史和外部结果保留 |

op restore 重建选定的本地历史状态，已经发生的外部发布仍然有效。
例如恢复旧的远端记录后，下一次发布还要面对服务器当前的 ref 和保留的发布 lease。

** 合并项目状态

项目和绑定使用 =Merge<Option<T>>= 保存候选值，项目按整条记录合并。
两边作相同修改可以收敛；不同改名、删除与修改等情况保留为冲突。

按 ID 合并之后，再检查名字、目录和关联约束。
两个不同 ID 的项目也可能同名或目录重叠，所以未解决定义的所有正项候选都参与占用检查。
同一连接的多绑定、悬空关联和观察归属不一致也会形成诊断。

诊断由状态推导，作用于相关项目和引用。健康项目可以继续使用，冲突通过 project resolve 等显式操作处理。
op diff/show 展示项目状态变化，project list/show/check 提供当前定义和诊断。

** 跨存储的本地修改

remote 生命周期涉及 Git config、refs 和 jj operation。系统先保存持久恢复记录，再按步骤应用修改。
日志保存原值、预期结果和多步 ref 修改的中间状态。仍有待恢复记录时，相关修改和传输暂停。

rollback 在原 operation 上恢复已记录的旧本地状态；accept 校验已提交的 operation 和本地结果，再完成待处理清理。
写锁与 ref 比较保护相应的修改步骤，遇到不兼容的外部更新时报告冲突。恢复只处理本地状态。

迁移使用同一恢复机制，在新 operation 提交后退役旧元数据。
迁移保留旧逻辑别名的完整拼写：parser 的 =parser-upstream= 仍叫 =parser-upstream=，不会剥掉前缀。物理配置键和 refs 重定位到独立 handle，已有 ConnectionId、BindingId、有效引用和转换记录保持身份。需要改成 origin 时，显式运行 =git remote rename --project parser parser-upstream origin=。
盘点和 apply 期间需要停止旧版及原生 Git 并发写者；恢复日志的基线建立后才开始相应校验。
维护操作步骤集中在使用指南末尾。

* 历史保存与导入

项目状态编码在 =simple_op_store_projects_v2= operation-store 中，包含 scoped remote 身份。格式标记区分能够保留这些语义的读写程序；恢复空项目状态仍使用同一格式。
读取旧 View 时保留其原有散列语义，格式升级通过显式迁移完成。

GC 将保留 View 中转换观察引用的 canonical commits 纳入根集合。
来源 raw 对象、normalization 和原生对应关系也需保留，以便旧观察继续解释历史和支持反向转换。
仓库备份因此包括操作元数据及来源对象库，而不仅是可见工作文件。

=project import= 直接读取本地 jj 仓库已记录的开发图，不经过独立 bundle 格式。
=--nested NAME=PATH= 将该来源开发图放进一个新外层项目，建立这个项目的定义和离线原生对应关系，不激活来源内部项目定义。
=--preserve NAME=PATH= 保留该来源项目、绑定、连接身份和稳定 label，只给 canonical 路径增加来源挂载前缀；项目引用保持原名，根引用加入来源名字前缀，不创建外层项目。
两种输入选项均可重复、混用，至少指定一个；来源名字跨模式唯一。=--mount NAME=DEST= 覆盖默认的 =NAME/= 挂载目录。所有来源参与同一次规划和发布事务，不使用全局模式开关。
仅导入真实书签，不将工作副本或 Git HEAD 状态改造成书签；未命名的导入版本通过保留的 change ID 选择。

保留模式同时迁入私有原生锚点、raw 对象、normalization generations 和 publication ledger；canonical ID 随提交映射，raw ID、endpoint 和 generation 不重新解释。ledger 独立于转换观察捕获，不能遗漏未跟踪分支或旧格式 lease。已有项目绑定的连接保留 URL、pushURL 和 remote 设置，fetch 目标引用由语义规划明确给出；配置层不根据物理名字推断作用域。不复制全局凭据配置，不自动 fetch 或 push。
项目身份复用、命名/目录冲突和不一致的转换依据均拒绝，不自动覆盖或更换身份。当前模型没有非项目的子目录作用范围，因此来源的 =RepositoryView= 绑定及其保留观察，以及有地址但未绑定项目的连接，在该模式下拒绝，不扩展存储格式。
两种模式共享来源捕获和发布生命周期，只保留不同的项目/引用/连接规划。图改写仅返回提交映射和统计，不生成模式专属 View；隐藏 canonical roots 显式传入而不伪装成可见 heads。完整 generation 的闭包批量验证，raw 对象仍使用独立的 shallow 边界。新 cache 完整填充后原子安装；主仓库配置、私有 refs 和本次导入的本地/remote mirrors 统一经过 remote-management journal，再提交目标操作。不可变对象和已完整安装的 cache 可在后续失败后留存，它们不代替发布操作。
普通 Git clone 运输 Git 历史，完整 jj 仓库备份则承担 operation history 等状态的保存。
