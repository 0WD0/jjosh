#+title: 使用 jjosh
#+options: toc:2 num:nil

本文以 =parser= 项目和 =libs/parser/= 目录为例。命令在目标 monorepo 的根目录运行；仓库创建和程序安装见 [[file:../README.org][README]]。
=parser-upstream= 是接收更新的来源，=parser-origin= 是自己的发布仓库。地址和分支名按实际情况替换。

* 准备项目

** 代码已经在当前仓库

例如，应用使用的 parser 位于 =libs/parser/=，现在准备为它建立独立的发布仓库：

#+begin_src sh
jjosh status
jjosh project add parser --path libs/parser
#+end_src

这样就建立了 =parser → libs/parser/= 的关联。接下来配置发布 remote，即可单独交付这个目录。
登记本身只记录项目定义；目录里的文件继续由 jj 管理。

** 代码在 Git 仓库

先选好本地目录，再配置来源：

#+begin_src sh
jjosh project add parser --path libs/parser
jjosh git remote add parser-upstream /path/to/parser.git \
  --project parser --whole
jjosh git fetch --remote parser-upstream --branch main
jjosh new @ main#parser@parser-upstream
#+end_src

=--whole= 把来源仓库的根目录放进 =libs/parser/=。
若来源是一个更大的仓库，只有其中的 =src/parser/= 属于这个项目，则将 remote add 写成：

#+begin_src sh
jjosh git remote add parser-upstream /path/to/components.git \
  --project parser --filter ':/src/parser' --base main
#+end_src

其余 fetch、new 步骤相同。=--base main= 为反向发布选择来源上下文，因此发布前需要获取这个分支。

** 代码在正在开发的 jj 仓库

要带入未发布的 change、分叉、空提交和原生冲突，使用 project import。
先在来源仓库运行 =jjosh status=，让工作文件进入已记录状态，再回到目标仓库执行：

#+begin_src sh
jjosh project import --source parser=/path/to/parser-work --mount parser=libs/parser
jjosh new @ workspace/default#parser
#+end_src

import 会一并登记项目。这一入口用于尚未登记的 parser；=default= 是来源 workspace 的名字。
需要一次带入多个项目时，重复指定 =--source= 和相应的 =--mount=。

来源的 change ID 会保留。目录和父提交的变化会生成新的 commit ID，失效的提交签名会移除并报告。
导入范围是来源已记录的开发状态和所需祖先历史；未记录文件及旧 operation/evolution history 留在来源仓库。

以后持续接收来源更新，为项目配置 whole remote：

#+begin_src sh
jjosh git remote add parser-upstream /path/to/parser-work --project parser --whole
#+end_src

无法直接读取来源目录时，可通过 bundle 运输。在来源运行 =jjosh native export /path/to/parser.bundle=；在目标运行 =native inspect= 检查，然后将 project import 的来源地址换成 bundle 路径。
bundle 还可携带来源的项目元数据，project import 以一个外层项目接入开发图；备份整个仓库时还需保存仓库元数据和来源对象库。

* 配置与外部仓库的关系

一个项目可以同时使用 upstream、fork 和发布仓库。每个 remote 都描述自己的地址和外部布局。

| 外部布局 | remote add 的选项 |
|----------+-------------------|
| 仓库根目录就是 parser | =--project parser --whole= |
| parser 位于 src/parser | =--project parser --filter ':/src/parser' --base main= |
| 布局与 parser-upstream 一致 | =--like parser-upstream= |
| 布局由版本化 workspace.josh 描述 | =--project parser --view PATH= |

=--view PATH= 使用来源各版本中 PATH 目录下的 =workspace.josh=。
=--like= 复用项目归属、布局表示和 base 选择规则；新 remote 使用自己的地址、远端记录和写权限。需要不同 base 时，直接指定 filter/view 和 base。

接收更新的转换 remote 默认只读。发布地址加 =--writable=：

#+begin_src sh
jjosh git remote add parser-origin /path/to/parser-fork.git \
  --like parser-upstream --writable
#+end_src

读取与发布使用不同地址时，add 还可指定 =--push-url URL=，这也会启用发布；显式 =--read-only= 优先。
普通 Git remote 沿用普通传输行为。

已经创建、尚未使用的普通 remote 可以补上项目映射：

#+begin_src sh
jjosh git remote attach parser-origin --project parser --whole --writable
#+end_src

attach 要求该 remote 没有绑定、获取记录或 tracking。来源映射在绑定创建时确定；另一种布局使用另一个 remote。
日后改地址用 =git remote set-url=，改别名用 =git remote rename=，停用连接用 =git remote remove=。

* 在同一张修改图上开发

应用和 parser 可以在同一个 change 中修改，也可以拆成相互依赖的多个 change。
照常用 describe 写说明，用 new 开始新修改，用 rebase 和 squash 整理历史。

** 接收更新

#+begin_src sh
jjosh git fetch --remote parser-upstream --branch main
jjosh log -r '@ | main#parser@parser-upstream'
#+end_src

fetch 更新远端记录。接下来根据修改图决定如何整合，例如将当前工作与新来源合在一起：

#+begin_src sh
jjosh new @ main#parser@parser-upstream
#+end_src

整合后在同一个工作目录中解决冲突、构建和测试应用及其依赖。

** 用书签选定交付版本

=topic#parser= 表示“将这个版本中的 parser 交付为 topic”。
后面的 =@parser-upstream= 则表示某个 remote 上的记录：

#+begin_example
topic#parser                    本地选定的 parser 版本
topic#parser@parser-upstream    上次从 parser-upstream 得到的 topic
#+end_example

创建交付书签：

#+begin_src sh
jjosh bookmark create topic#parser -r @
#+end_src

后续选择其他版本时，用 =bookmark set topic#parser -r REV=。
书签指向的是完整提交；parser 的内容范围在发布时根据项目定义选取。

若希望本地 main 随来源更新而合并移动，开启 tracking：

#+begin_src sh
jjosh bookmark track main#parser@parser-upstream
#+end_src

fetch 默认将新远端书签保留为 untracked，工作头由你通过 new 等命令选择。

* 发布修改

** 发布分支

先准备目标 Git 仓库，并配置好可写的 parser-origin。
目标已有相应分支时，获取它的状态；例如：

#+begin_src sh
jjosh git fetch --remote parser-origin --branch main
#+end_src

书签已经跟踪其他 remote 时，首次向新目标发布前，用 =bookmark track NAME@REMOTE= 建立对这个目标的跟踪。

整理待交付历史，为其中的修改写好说明，解决所选项目中的冲突，然后检查发布计划：

#+begin_src sh
jjosh git push --remote parser-origin --bookmark topic#parser --dry-run
#+end_src

计划列出实际发布地址、项目目录、所用来源映射、远端 ref，以及更新前后的 Git 对象 ID。
确认后执行：

#+begin_src sh
jjosh git push --remote parser-origin --bookmark topic#parser
#+end_src

远端收到 =topic= 分支。whole 绑定将 parser 放在远端根目录；上面的 filter 示例则将它放回 =src/parser/=。

发布到空仓库时，whole 绑定可以直接进行首次 push。
filtered 绑定需要可用的来源上下文；若空目标无法提供配置的 base，使用下文的一次性导出。

** 同时发布几个项目

为各项目创建交付书签后，可以一次选择它们：

#+begin_src sh
jjosh git push --bookmark 'topic#*' --dry-run
#+end_src

在没有显式 =--remote= 或 =git.push= 配置时，命令为每个项目选择唯一可写的绑定。
有多个可写地址时，用 =--remote= 明确选择。引用模式加引号，交给 jjosh 而不是 shell 展开。

所有目标先完成预检，再开始发布。不同服务器之间无法原子提交；若发生部分失败，以命令报告的各目标结果为准。

** 发布版本 tag

#+begin_src sh
jjosh tag set v1.0#parser -r topic#parser
jjosh git push --remote parser-origin --tag v1.0#parser
#+end_src

远端 tag 名为 =v1.0=。支持轻量 tag 和未签名的 annotated commit tag；签名 tag 的转换会被拒绝。
tag 的不可变规则可能让当前工作副本移到新的子提交。

移动已有 tag 使用 =tag set --allow-move=；删除使用 =tag delete=，随后 push 对应 tag 的删除。
从远端获取 tag 后，可用 =tag track= 建立本地跟踪。

** 一次性导出

例如，想把 parser 按 upstream 的目录结构导出到一个空 Git 仓库：

#+begin_src sh
jjosh git remote add parser-export /path/to/empty-parser.git
jjosh bookmark track topic#parser@parser-export
jjosh git push --remote parser-export --source parser-upstream \
  --bookmark topic#parser --dry-run
#+end_src

检查后去掉 =--dry-run=。这里 parser-upstream 提供转换方式和已获取的来源上下文，parser-export 提供发布地址。
持续双向同步使用带项目绑定的 remote；已有绑定的目标始终使用自己的表示。

** 目标被别人更新了

发布会校验目标 ref 的精确 Git 对象 ID，这份更新依据称为 lease。
出现 stale lease 时，重新获取实际发布目标，再决定如何整合或重写。annotated tag 只修改注释，也会改变对象 ID。

upstream、fork 和镜像各有自己的状态。发布目标的 lease 必须来自那个实际地址；=--force= 不能绕过这项保护。

* 选择历史和检出布局

** 调整工作目录

如果只构建 parser，可以把完整树中的 =libs/parser/= 检出到工作目录根部：

#+begin_src sh
jjosh sparse set root:libs/parser
jjosh sparse map set libs/parser=.
#+end_src

随后在根目录编辑和构建，修改仍记录到提交中的 =libs/parser/=。
这种映射需要非 colocated 工作树。=sparse map reset= 恢复原路径映射，=sparse reset= 恢复完整检出。
多目录规则见 [[file:../jj/docs/filesets.md][filesets 文档]]。

** 只取一部分来源历史

Git filter/view 来源首次获取可加 =--depth 1=。后续按需要增加深度：

#+begin_src sh
jjosh --config git.abandon-unreachable-commits=false \
  git fetch --remote parser-upstream --branch main --deepen 50
#+end_src

要补全剩余历史，将 =--deepen 50= 换成 =--unshallow=。
这项配置保留原来的浅边界版本，便于随后显式整合；当前自动放弃旧边界并重写本地后继的路径可能触发 root merge 错误。

浅边界按来源地址隔离。向缺少所需祖先的目标发布时，可能要先补全历史。
普通 remote 和本地 jj 原生来源使用完整获取。

** 获取指定 commit 或使用镜像

#+begin_src sh
jjosh git fetch --remote parser-upstream --revision OID
#+end_src

将 OID 替换为来源完整 commit ID。输出中的 =Fetched revision RAW as CANONICAL= 给出本地应使用的 commit ID。
此方式直接带入指定版本；=--revision= 可重复，要求服务器允许获取该对象，并与 =--tracked= 互斥。本地 jj 原生来源不支持 raw OID 选择。

临时从镜像获取：

#+begin_src sh
jjosh git fetch --remote parser-upstream --branch main --fetch-url /path/to/parser-mirror.git
#+end_src

=--revision= 和 =--fetch-url= 都要求恰好选中一个 named remote。镜像地址仅用于本次获取，发布仍依据目标自己的状态。

** 建立整个仓库的过滤视图

在另一个目标仓库中，为整个仓库配置 filter：

#+begin_src sh
jjosh git remote add upstream /path/to/components.git --filter ':/src/parser'
jjosh git fetch --remote upstream --branch main
jjosh new main@upstream
#+end_src

这里没有 =--project=，过滤结果直接成为仓库根内容，引用使用 =main@upstream=。
可用 =--view PATH= 选择版本化布局；需要发布时配置可写绑定。

临时查看当前仓库某个 filter 的结果，使用：

#+begin_src sh
jjosh projection preview ':/libs/parser' -r @ --files --history
#+end_src

preview 对已记录的版本求值，可加 =--json= 或改用 =--view PATH=。
结果用于查看过滤后的内容和历史；向具体 remote 交付的结果用 push dry-run 检查。

* 仓库维护

** 查看和调整项目

=project list= 列出项目，=project show parser= 查看目录、label 和绑定，=project check= 检查全仓库的项目状态。
这些命令离线工作并支持 =--json=；=project check parser= 可单独检查 parser。

项目显示名用 =project rename parser syntax= 修改。目录和引用 label 保持原值，因此书签仍叫 =topic#parser=。
当前项目各占一个非根目录，目录之间互不重叠；路径与 label 的整体迁移尚无专用命令。

停止维护一个项目时，先处理它的绑定、引用及 tracking，再用 =project remove= 注销。文件和提交继续保留。
项目定义冲突会显示候选项：=project resolve --id ID --candidate N= 选择项目定义，=--name NAME= 解决显示名；绑定和 label 分别用 =--binding ID=、=--label LABEL= 选择。=--delete= 用于删除所选定义，仍需先处理依赖。

** 恢复操作

op restore 按所选部分恢复状态：repo 包含项目定义、绑定和本地引用，remote-tracking 包含远端记录及转换依据。
本地连接地址、写权限和已经发生的外部发布独立保存。

删除 remote 后再同名创建，会得到一个新连接。若恢复出来的旧远端记录占用了这个名字，可以明确清理它们：

#+begin_src sh
jjosh git remote forget-observations parser-origin
#+end_src

该操作清除远端记录、tracking 和对应缓存 mirror，保留本地书签、tag、项目、绑定、源码及来源对象。
随后重新 fetch，并按需要开启 tracking。已断开的旧绑定可按其 ID 用 =project resolve --binding ID --delete= 停用。

** 处理 remote 修改中断

按报错提示选择恢复方式：

| 命令 | 结果 |
|------+------|
| =git remote recover --rollback= | 在原 operation 上恢复记录的旧本地状态 |
| =git remote recover --accept= | 校验已提交状态，保留修改并完成待处理清理 |

恢复在本地进行。外部配置或 ref 已发生不兼容修改时，先处理报出的差异；仍在使用的 Git 锁文件应交给对应进程释放。

** 升级旧仓库

升级前备份仓库元数据和来源对象库，停止不兼容的 jj 进程及原生 Git 并发写者。进入待迁移仓库查看计划：

#+begin_src sh
jjosh project migrate --dry-run
#+end_src

计划列出项目目录、来源表示、引用处理及将退役的旧元数据。省略 =--dry-run= 也只显示计划。
根据诊断补充选择：

| 选项 | 用途 |
|------+------|
| =--representation REMOTE=whole= | 指定整个来源作为项目内容 |
| =--representation REMOTE=filter:EXPR= | 指定项目挂载前的来源 filter |
| =--representation REMOTE=view:PATH= | 指定来源 view |
| =--clear-observations REMOTE= | 清除缺少可靠转换依据的旧远端记录，之后重新获取 |
| =--native-source PROJECT=REMOTE= | 将原生对应关系归给同项目的 whole 绑定 |
| =--native-source PROJECT=detached= | 保留离线原生对应关系；这是默认选择 |

例如，确认来源布局为 =src/parser/=，并需要重建其远端记录：

#+begin_src sh
jjosh project migrate --dry-run \
  --representation 'parser-upstream=filter::/src/parser' --clear-observations parser-upstream
jjosh project migrate --apply --exclusive \
  --representation 'parser-upstream=filter::/src/parser' --clear-observations parser-upstream
jjosh project check
jjosh git fetch --remote parser-upstream --branch main
#+end_src

迁移保留本地引用、工作文件、来源对象、浅边界、发布 lease 及有效连接配置。
include/global 中的 remote 设置需要先整理到本地；孤立 sidecar 和配置冲突按计划中的诊断处理。

从计划到 apply 结束都应保持维护窗口。=--exclusive= 是停止不兼容写者的确认，而非全局 Git 锁；日志建立前的并发写入不受恢复校验保护。
项目状态使用 =simple_op_store_projects_v1= 格式，旧程序无法写入；迁移中断按上面的 remote recover 步骤处理。

备份应覆盖仓库元数据和来源对象库。历史转换目前要求 SHA-1 Git backend；gitlink 保留为引用，不递归展开。
原生 Git 直接操作外部仓库，因此过滤和本地只读配置都不能充当访问控制。
