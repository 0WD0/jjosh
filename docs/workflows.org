#+title: 使用 jjosh
#+options: toc:2 num:nil

本文以 =parser= 项目和 =libs/parser/= 目录为例。命令在目标 monorepo 的根目录运行；仓库创建和程序安装见 [[file:../README.org][README]]。
每个项目独立使用自己的 remote 名字。示例以 =origin= 为日常双向连接，=fork= 为另一个同项目连接；地址和分支名按实际情况替换。

* 准备项目

** 代码已经在当前仓库

例如，应用使用的 parser 位于 =libs/parser/=，现在准备为它建立独立的发布仓库：

#+begin_src sh
jjosh status
jjosh project add parser --path libs/parser
#+end_src

这样就建立了 =parser → libs/parser/= 的关联。接下来配置发布 remote，即可单独交付这个目录。
登记本身只记录项目定义；目录里的文件继续由 jj 管理。

** 代码在 Git 仓库

先选好本地目录，再配置来源：

#+begin_src sh
jjosh project add parser --path libs/parser
jjosh git remote add origin /path/to/parser.git \
  --project parser --whole
jjosh git fetch --project parser --branch main
jjosh new @ main#parser@origin
#+end_src

=--whole= 把来源仓库的根目录放进 =libs/parser/=。
若来源是一个更大的仓库，只有其中的 =src/parser/= 属于这个项目，则将 remote add 写成：

#+begin_src sh
jjosh git remote add origin /path/to/components.git \
  --project parser --filter ':/src/parser' --base main
#+end_src

其余 fetch、new 步骤相同。=--base main= 为反向发布选择来源上下文，因此发布前需要获取这个分支。

** 代码在正在开发的 jj 仓库

要带入未发布的 change、分叉、空提交和原生冲突，使用 project import。
先在来源仓库运行 =jjosh status=，让工作文件进入已记录状态，再回到目标仓库执行：

#+begin_src sh
source_change=$(jjosh --ignore-working-copy -R /path/to/parser-work log -r @ --no-graph -T change_id)
jjosh project import --source parser=/path/to/parser-work --mount parser=libs/parser
jjosh new @ "$source_change"
#+end_src

import 会一并登记项目。这一入口用于尚未登记的 parser；来源必须是本地 jj workspace 目录。
需要一次带入多个项目时，重复指定 =--source= 和相应的 =--mount=。

来源的 change ID 会保留。目录和父提交的变化会生成新的 commit ID，失效的提交签名会移除并报告。
导入范围是来源已记录的开发状态和所需祖先历史；未记录文件及旧 operation/evolution history 留在来源仓库。
导入不会创建 =workspace/*= 或 Git HEAD 书签，也不会迁入来源 workspace。已有书签按项目限定名保留，例如 =main#parser=；没有书签的版本可用来源 change ID 选择。用户自己命名为 =workspace/default= 的书签仍按普通书签保留。

以后持续接收来源更新，为项目配置 whole remote：

#+begin_src sh
jjosh git remote add upstream /path/to/parser-work --project parser --whole
#+end_src

来源 remote 的名字保存在新外层项目中，连接地址由你另行配置。内部项目的 =origin#inner= 导入为外层项目内的 =origin@inner=，来源 Git 工作树记录使用 =git@source=；命令会列出这些明确映射并拒绝重名。引用中的 remote 含 =@= 时加引号，例如 =main#inner#parser@"origin@inner"=。

* 配置与外部仓库的关系

一个项目可以同时使用 origin、upstream、fork 和发布仓库。每个 remote 都能 fetch 和 push，并描述自己的地址和外部布局。根、parser 和其他项目可以各自拥有同名 remote。

| 外部布局 | remote add 的选项 |
|----------+-------------------|
| 仓库根目录就是 parser | =--project parser --whole= |
| parser 位于 src/parser | =--project parser --filter ':/src/parser' --base main= |
| 布局与 parser 的 origin 一致 | =--like origin#parser= |
| 布局由版本化 workspace.josh 描述 | =--project parser --view PATH= |

=--view PATH= 使用来源各版本中 PATH 目录下的 =workspace.josh=。
=--like= 复用项目归属、布局表示和 base 选择规则；新 remote 使用自己的地址和远端记录。需要不同 base 时，直接指定 filter/view 和 base。

配置自己的 fork，例如：

#+begin_src sh
jjosh git remote add fork /path/to/parser-fork.git \
  --like origin#parser
#+end_src

fetch 和 push 默认使用同一个 URL。读取与发布使用不同地址时，add 可指定 =--push-url URL=；后续用 =git remote set-url --project parser fork --push URL= 修改发布地址。

已经创建、尚未使用的普通 remote 可以补上项目映射：

#+begin_src sh
jjosh git remote attach fork --project parser --whole
#+end_src

attach 要求该根 remote 没有绑定、获取记录或 tracking。它把连接移入项目，释放原来的根名字；ConnectionId 保持不变。来源映射在绑定创建时确定，另一种布局使用另一个 remote。

选择项目后管理其本地名字，或直接使用 =NAME#LABEL=：

#+begin_src sh
jjosh git remote list --project parser
jjosh git remote rename --project parser fork publish
jjosh git remote set-url publish#parser /path/to/new-fork.git
jjosh git remote rename --project parser publish fork
#+end_src

=--project= 使用项目显示名，=#LABEL= 使用稳定引用 label。省略范围时选择根；=origin#= 明确选择根的 origin。给出两个不同范围时拒绝执行。
上述例子最后把名字改回 fork，后续命令继续使用它。remote 改名保留 ConnectionId 和 BindingId，也不改变实际 Git handle；项目显示名变化保留 ProjectId 和引用 label。

** 项目的默认 remote

未设置默认值时，只有一个 remote 就使用它；有多个 remote 则选择该项目的 origin，没有 origin 就报告歧义。
例如，保留从 origin 获取，只把发布改到 fork：

#+begin_src sh
jjosh config set --repo git.projects.parser.push fork
jjosh git fetch --project parser --branch main
jjosh git push --bookmark topic#parser
#+end_src

项目配置支持与 jj 相同的名字、模式和列表。需要从两个连接收取时，可以写：

#+begin_src toml
[git.projects.parser]
fetch = ["origin", "fork"]
push = "fork"
#+end_src

配置段中的 parser 是引用 label；值中的 remote 名只在该项目内解析。模式同样限制在项目内，例如 =fetch = "glob:up*"=。
选择顺序是显式 =--remote=、项目对应的 fetch/push 配置、项目唯一 remote、项目内的 origin。仍无法确定时报告歧义；错误配置不会回退到其他连接。

根操作使用 =git.fetch=／=git.push= 和根的 remotes。项目操作独立选择自己的配置，不继承根默认值。=git fetch --project parser --all-remotes= 收取该项目的全部连接；不带项目选择的 =--all-remotes= 只选择根。
push 根据所选书签或 tag 的 =#LABEL= 选择项目。URL、push URL、tracking、创建顺序和名字前缀都不决定默认目的地。

每个连接的自动跟踪和默认获取引用设置使用限定名，例如：

#+begin_src toml
[remotes."origin#parser"]
auto-track-bookmarks = "main"
#+end_src

=remotes.origin= 只配置根的 origin。项目 remote 的 rename/remove 只调整本地仓库中对应项目的默认值和限定名设置；用户级设置需自行维护。默认配置不随 op restore 恢复。

* 在同一张修改图上开发

应用和 parser 可以在同一个 change 中修改，也可以拆成相互依赖的多个 change。
照常用 describe 写说明，用 new 开始新修改，用 rebase 和 squash 整理历史。

** 接收更新

#+begin_src sh
jjosh git fetch --project parser --remote origin --branch main
jjosh log -r '@ | main#parser@origin'
#+end_src

fetch 更新远端记录。接下来根据修改图决定如何整合，例如将当前工作与新来源合在一起：

#+begin_src sh
jjosh new @ main#parser@origin
#+end_src

整合后在同一个工作目录中解决冲突、构建和测试应用及其依赖。

** 一次接收多个项目

为 app 也登记项目并配置连接后，可以选择指定项目，或全部未删除的登记项目：

#+begin_src sh
jjosh git fetch --project parser --project app --branch main
jjosh git fetch --all-projects --branch main
jjosh git fetch --all-projects --all-remotes
#+end_src

=--project= 可重复，重复项目会去重；它与 =--all-projects= 互斥。这两种选择都不包含根。没有项目选择时只操作根；根的 origin 可以显式写成 =--remote origin#=。
每个项目分别解析 =--remote= 名字或模式、=git.projects.LABEL.fetch=，再采用唯一连接／origin 规则。=--all-remotes= 则展开每个选中项目的全部连接。
例如 =--project parser --project app --remote origin= 要求两个项目各自有 origin，不能从根借用。任何一个项目缺少显式别名，都会在第一个网络请求之前报错。

整批项目、配置和连接先完成预检。=--all-projects= 包含未删除项目的冲突候选，遇到未解决定义会报错；没有活动连接的离线项目也不会被悄悄跳过。
预检不保证服务器可达。后续网络失败仍可能留下部分获取结果，也不会替你整合工作头；按命令报告处理各连接的结果。

** 用书签选定交付版本

=topic#parser= 表示“将这个版本中的 parser 交付为 topic”。
后面的 =@origin= 表示该项目 origin 上的记录：

#+begin_example
topic#parser           本地选定的 parser 版本
topic#parser@origin    上次从 parser 的 origin 得到的 topic
#+end_example

创建交付书签：

#+begin_src sh
jjosh bookmark create topic#parser -r @
#+end_src

后续选择其他版本时，用 =bookmark set topic#parser -r REV=。
书签指向的是完整提交；parser 的内容范围在发布时根据项目定义选取。

若希望本地 main 随来源更新而合并移动，开启 tracking：

#+begin_src sh
jjosh bookmark track main#parser@origin
#+end_src

fetch 默认将新远端书签保留为 untracked，工作头由你通过 new 等命令选择。

* 发布修改

** 发布分支

先准备目标 Git 仓库，并为 parser 配置好 fork。
目标已有相应分支时，获取它的状态；例如：

#+begin_src sh
jjosh git fetch --project parser --remote fork --branch main
#+end_src

书签已经跟踪其他 remote 时，首次向新目标发布前，用 =bookmark track NAME@REMOTE= 建立对这个目标的跟踪。

整理待交付历史，为其中的修改写好说明，解决所选项目中的冲突，然后检查发布计划：

#+begin_src sh
jjosh git push --remote fork --bookmark topic#parser --dry-run
#+end_src

计划列出实际发布地址、项目目录、所用来源映射、远端 ref，以及更新前后的 Git 对象 ID。
确认后执行：

#+begin_src sh
jjosh git push --remote fork --bookmark topic#parser
#+end_src

远端收到 =topic= 分支。whole 绑定将 parser 放在远端根目录；上面的 filter 示例则将它放回 =src/parser/=。

发布到空仓库时，whole 绑定可以直接进行首次 push。
filtered 绑定需要可用的来源上下文；若空目标无法提供配置的 base，使用下文的一次性导出。

** 同时发布几个项目

为各项目创建交付书签后，可以一次选择它们：

#+begin_src sh
jjosh git push --bookmark 'glob:topic#*' --dry-run
#+end_src

每个项目分别解析自己的默认发布 remote，也可以用同一个本地名字选择它们的目的地：

#+begin_src sh
jjosh git push --remote fork --bookmark 'glob:topic#*' --dry-run
#+end_src

这里的 fork 分别指 parser 的 fork、app 的 fork，依此类推。任何被选项目缺少 fork 时，整批操作在发布前报错。=glob:= 显式启用模式，外层引号防止 shell 展开。
选择依据是每个引用的 label，而不是提交修改的目录；普通根引用使用根默认值，项目引用不继承它。需要显式选择根连接时写 =--remote origin#=，而不是依赖项目中找不到 origin 时回退。

所有目标先完成预检，再开始发布。不同服务器之间无法原子提交；若发生部分失败，以命令报告的各目标结果为准。

** 发布版本 tag

#+begin_src sh
jjosh tag set v1.0#parser -r topic#parser
jjosh git push --remote fork --tag v1.0#parser
#+end_src

远端 tag 名为 =v1.0=。支持轻量 tag 和未签名的 annotated commit tag；签名 tag 的转换会被拒绝。
tag 的不可变规则可能让当前工作副本移到新的子提交。

移动已有 tag 使用 =tag set --allow-move=；删除使用 =tag delete=，随后 push 对应 tag 的删除。
从远端获取 tag 后，可用 =tag track= 建立本地跟踪。

** 一次性导出

例如，想把 parser 按 upstream 的目录结构导出到一个空 Git 仓库：

#+begin_src sh
jjosh git remote add export /path/to/empty-parser.git
jjosh bookmark track topic#parser@export#
jjosh git push --remote export# --source origin#parser \
  --bookmark topic#parser --dry-run
#+end_src

检查后去掉 =--dry-run=。这里 origin#parser 提供转换方式和已获取的来源上下文，根的 export 提供发布地址。引用 =topic#parser@export#= 用末尾的空 scope 明确选择根连接，不会被解释为 parser 内的 export。
持续双向同步使用带项目绑定的 remote；已有绑定的目标始终使用自己的表示。

** 目标被别人更新了

发布会校验目标 ref 的精确 Git 对象 ID，这份更新依据称为 lease。
出现 stale lease 时，重新获取实际发布目标，再决定如何整合或重写。annotated tag 只修改注释，也会改变对象 ID。

upstream、fork 和镜像各有自己的状态。发布目标的 lease 必须来自那个实际地址；=--force= 不能绕过这项保护。

* 选择历史和检出布局

** 调整工作目录

如果只构建 parser，可以把完整树中的 =libs/parser/= 检出到工作目录根部：

#+begin_src sh
jjosh sparse set root:libs/parser
jjosh sparse map set libs/parser=.
#+end_src

随后在根目录编辑和构建，修改仍记录到提交中的 =libs/parser/=。
这种映射需要非 colocated 工作树。=sparse map reset= 恢复原路径映射，=sparse reset= 恢复完整检出。
多目录规则见 [[file:../jj/docs/filesets.md][filesets 文档]]。

** 只取一部分来源历史

Git filter/view 来源首次获取可加 =--depth 1=。后续按需要增加深度：

#+begin_src sh
jjosh --config git.abandon-unreachable-commits=false \
  git fetch --project parser --remote origin --branch main --deepen 50
#+end_src

要补全剩余历史，将 =--deepen 50= 换成 =--unshallow=。
这项配置保留原来的浅边界版本，便于随后显式整合；当前自动放弃旧边界并重写本地后继的路径可能触发 root merge 错误。

浅边界按来源地址隔离。向缺少所需祖先的目标发布时，可能要先补全历史。
普通 remote 和本地 jj 原生来源使用完整获取。

** 获取指定 commit 或使用镜像

#+begin_src sh
jjosh git fetch --project parser --remote origin --revision OID
#+end_src

将 OID 替换为来源完整 commit ID。输出中的 =Fetched revision RAW as CANONICAL= 给出本地应使用的 commit ID。
此方式直接带入指定版本；=--revision= 可重复，要求服务器允许获取该对象，并与 =--tracked= 互斥。本地 jj 原生来源不支持 raw OID 选择。

临时从镜像获取：

#+begin_src sh
jjosh git fetch --project parser --remote origin --branch main --fetch-url /path/to/parser-mirror.git
#+end_src

=--revision= 和 =--fetch-url= 都要求整批解析、去重后恰好选中一个物理 named remote，即使多个项目中的连接都叫 origin，也不能合并视为一个。镜像地址仅用于本次获取，发布仍依据目标自己的状态。

** 建立整个仓库的过滤视图

在另一个目标仓库中，为整个仓库配置 filter：

#+begin_src sh
jjosh git remote add upstream /path/to/components.git --filter ':/src/parser'
jjosh git fetch --remote upstream --branch main
jjosh new main@upstream
#+end_src

这里没有 =--project=，过滤结果直接成为仓库根内容，引用使用 =main@upstream=。
可用 =--view PATH= 选择版本化布局；发布仍使用 git push。

临时查看当前仓库某个 filter 的结果，使用：

#+begin_src sh
jjosh projection preview ':/libs/parser' -r @ --files --history
#+end_src

preview 对已记录的版本求值，可加 =--json= 或改用 =--view PATH=。
结果用于查看过滤后的内容和历史；向具体 remote 交付的结果用 push dry-run 检查。

* 仓库维护

** 查看和调整项目

=project list= 列出项目，=project show parser= 查看目录、label、绑定和各连接的 scoped 名字，=project check= 检查全仓库的项目状态。
这些命令离线工作并支持 =--json=；=project check parser= 可单独检查 parser。

项目显示名用 =project rename parser syntax= 修改。目录和引用 label 保持原值，因此书签仍叫 =topic#parser=。
当前项目各占一个非根目录，目录之间互不重叠；路径与 label 的整体迁移尚无专用命令。

停止维护一个项目时，先处理它的绑定、引用及 tracking，再用 =project remove= 注销。文件和提交继续保留。
项目定义冲突会显示候选项：=project resolve --id ID --candidate N= 选择项目定义，=--name NAME= 解决显示名；绑定和 label 分别用 =--binding ID=、=--label LABEL= 选择。=--delete= 用于删除所选定义，仍需先处理依赖。
remote 名字的冲突用 =project resolve --connection CONNECTION_ID --candidate N= 选择候选，或用 =--name NAME= 明确命名。作用范围来自该连接的项目身份，不能用改名把它移到另一个项目。

** 恢复操作

op restore 按所选部分恢复状态：repo 包含项目定义、绑定和本地引用，remote-tracking 包含 remote 的项目内名字、连接归属、远端记录及转换依据。
本地连接地址、认证配置和已经发生的外部发布独立保存。

删除 remote 后再同名创建，会得到一个新连接。恢复旧 remote-tracking 状态会恢复旧连接的名字和记录，不会把它们转交给新连接。可以明确清理已断开的旧记录：

#+begin_src sh
jjosh git remote forget-observations fork#parser
#+end_src

该操作清除所选连接的远端记录、tracking 和缓存 mirror；已断开连接的 scoped 名字一并退役，仍活动的连接保留名字。它保留本地书签、tag、源码及来源对象。
如果新连接的名字被历史恢复覆盖，先在 =project show parser= 中找到当前绑定的 ConnectionId，再用 =project resolve --connection ID --name fork= 明确恢复其名字，随后重新 fetch。该操作校验实际连接和项目绑定，不根据同名或唯一候选猜测身份。
已断开的旧绑定可按其 ID 用 =project resolve --binding ID --delete= 停用。

** 处理 remote 修改中断

按报错提示选择恢复方式：

| 命令 | 结果 |
|------+------|
| =git remote recover --rollback= | 在原 operation 上恢复记录的旧本地状态 |
| =git remote recover --accept= | 校验已提交状态，保留修改并完成待处理清理 |

恢复在本地进行。外部配置或 ref 已发生不兼容修改时，先处理报出的差异；仍在使用的 Git 锁文件应交给对应进程释放。

** 升级旧仓库

升级前备份仓库元数据和来源对象库，停止不兼容的 jj 进程及原生 Git 并发写者。进入待迁移仓库查看计划：

#+begin_src sh
jjosh project migrate --dry-run
#+end_src

计划列出项目目录、来源表示、scoped 名字、内部连接重定位、引用处理及将退役的旧元数据。省略 =--dry-run= 也只显示计划。
已有项目格式也通过显式迁移建立 remote 命名空间：旧别名逐字保留，例如 =parser-upstream= 变为 parser 项目内的 =parser-upstream=，不会自动去掉前缀。内部 Git 键会迁到独立 handle，ConnectionId、BindingId、有效引用和转换记录保持原有身份。需要简化名字时，迁移后运行 =git remote rename --project parser parser-upstream origin=。
废弃的 =remote.NAME.jjosh-readOnly= 也在计划中清理。仓库内 =remotes.NAME= 设置移到限定名；用户级或 include/global 设置先按诊断整理。项目默认值独立生效，原先用于选择项目连接的 =git.fetch=／=git.push= 应改配到对应项目。
迁移可以完全离线完成，不要求重新 fetch。默认保留旧远端引用、跟踪状态和 canonical mirror；它们仍是历史缓存，不会因此获得原本缺失的来源转换证据或新的发布 lease。依赖这些证据的发布仍需通过原有检查，不能把保留缓存等同于验证了远端当前状态。
根据诊断补充选择：

| 选项 | 用途 |
|------+------|
| =--representation REMOTE=whole= | 指定整个来源作为项目内容 |
| =--representation REMOTE=filter:EXPR= | 指定项目挂载前的来源 filter |
| =--representation REMOTE=view:PATH= | 指定来源 view |
| =--clear-observations REMOTE= | 可选：显式清除旧远端记录、跟踪和 canonical mirror；不是迁移前提 |
| =--native-source PROJECT=REMOTE= | 将原生对应关系归给同项目的 whole 绑定 |
| =--native-source PROJECT=detached= | 保留离线原生对应关系；这是默认选择 |

例如，确认来源布局为 =src/parser/=，保留已有远端记录并离线迁移：

#+begin_src sh
jjosh project migrate --dry-run \
  --representation 'parser-upstream=filter::/src/parser'
jjosh project migrate --apply --exclusive \
  --representation 'parser-upstream=filter::/src/parser'
jjosh project check
#+end_src

迁移保留本地引用、工作文件、来源对象、浅边界、发布 lease 及有效连接配置。
include/global 中的 remote 设置需要先整理到本地；孤立 sidecar 和配置冲突按计划中的诊断处理。

从计划到 apply 结束都应保持维护窗口。=--exclusive= 是停止不兼容写者的确认，而非全局 Git 锁；日志建立前的并发写入不受恢复校验保护。
项目状态使用 =simple_op_store_projects_v2= 格式，旧程序无法写入；旧操作仍按原来记录的身份读取。迁移中断按上面的 remote recover 步骤处理。

备份应覆盖仓库元数据和来源对象库。历史转换目前要求 SHA-1 Git backend；gitlink 保留为引用，不递归展开。
原生 Git 直接操作外部仓库，过滤不能充当访问控制；访问权限由服务器管理。
