#+title: jjosh 使用指南
#+options: toc:2 num:nil

本文讲当前已实现的工作流。安装和最短示例见 [[file:../README.org][README]]；模型细节见[[file:subprojects-design.org][项目与 remote 模型]]。
[[file:scoped-references-design.org][类型化本地引用]]仍是提案，不应当作现有 CLI 使用。

例子以项目 =parser=、本地目录 =libs/parser/=、分支 =main= 为约定。
除创建仓库和读取来源状态外，命令在目标仓库根目录执行。=/path/to/…=、=OID=、=OP=、=ID= 等必须替换为实际路径或命令输出中的值；分支、项目和书签也要按自己的仓库调整。
互为替代的接入例子不要在同一个已登记项目上重复执行。

* 先分清四件事

- *项目*：本地完整树中的一块目录，例如 parser 对应 =libs/parser/=。项目有显示名和稳定引用 label；改显示名不会改 label 或目录。
- *逻辑 remote*：项目内的命名连接，例如 =origin#parser=，以及它采用的外部布局。根和每个项目可以各有一个 origin；同名不等于同一个连接。
- *本地传输配置*：实际 Git URL、push URL、认证和当前 Git 同步状态。没有地址的逻辑 remote 仍可存在，但不能凭历史记录联网。
- *历史观察*：曾经从哪个连接看到哪些远端引用、跟踪关系和转换依据。它不是当前连接目录，更不是服务器当前状态的保证。

常用名字这样读：

| 名字 | 当前用途 |
|------+----------|
| =main= | 根的本地书签 |
| =main#parser= | 选定 parser 交付版本的本地书签 |
| =main#parser@origin= | parser 的 origin 上已记录的 main |
| =origin#parser= | 在管理或同步命令中选择 parser 的 origin |
| =origin#= | 明确选择根的 origin |

这里的后缀参与当前命令的范围解析，但不是完整的类型化身份。
项目书签仍指向完整提交；发布时才根据项目与绑定选取内容。引用名不能独自证明它来自哪个服务器、哪种转换或哪次观察。
=--project parser= 按项目显示名选择，=#parser= 按稳定 label 选择；两个范围不一致会报错。

* 把代码放进本地修改图

** 目标仓库与已有目录

新建目标仓库：

#+begin_src sh
jjosh git init --no-colocate --object-hash sha1 mono
cd mono
jjosh describe -m 'Start monorepo'
#+end_src

已有代码在 =libs/parser/= 时，只登记目录即可：

#+begin_src sh
jjosh status
jjosh project add parser --path libs/parser
#+end_src

登记不搬文件、不改提交。项目目前各占一个非根目录，目录不能重叠。
目录也可以尚未出现，随后从来源获取内容。

** 从 Git 仓库带入

对于尚未登记的 parser：

#+begin_src sh
jjosh project add parser --path libs/parser
jjosh git remote add origin /path/to/parser.git --project parser --whole
jjosh git fetch --project parser --branch main
jjosh new @ main#parser@origin
#+end_src

外部仓库根目录成为 =libs/parser/=。若只要大仓库里的 =src/parser/=，把 remote add 换成：

#+begin_src sh
jjosh git remote add origin /path/to/components.git \
  --project parser --filter ':/src/parser' --base main
#+end_src

仍按前面的 fetch、new 整合。filter 和 base 的选择见后面的“连接不同的外部布局”。

** 从本地 jj workspace 带入原生开发状态

原生 import 适合未发布的 change、分叉、空提交和原生冲突。
先在来源执行 =jjosh status=，把工作文件记录下来。目标不得已经登记这个 parser：

#+begin_src sh
source_change=$(jjosh --ignore-working-copy -R /path/to/parser-work log -r @ --no-graph -T change_id)
jjosh project import --nested parser=/path/to/parser-work --mount parser=libs/parser
jjosh new @ "$source_change"
#+end_src

=--nested= 将整个来源包进一个新外层项目，并登记项目。
change ID 保留；挂载路径和父提交变化会产生新 commit ID，失效的提交签名会移除并报告。
导入范围是来源已记录的开发状态及所需祖先，不包含未记录文件、旧 operation/evolution history 或来源 workspace。
import 本身不切换、不整合目标工作副本，所以最后显式使用 new。

来源书签会加外层限定，例如 =main#parser=；已有内层限定继续保留，例如 =main#inner#parser=。
没有书签的版本可以用来源 change ID 选择。
不会凭空创建 =workspace/*= 或 Git HEAD 书签；用户自己创建的 =workspace/default= 仍是普通书签。

来源真实 remote 只带入*历史身份和观察*，不会激活目标的同名逻辑 remote，也不带入其传输配置。
因此导入后可以直接建立日常连接，无需先清理旧观察：

#+begin_src sh
jjosh git remote add origin /path/to/parser-work --project parser --whole
#+end_src

指向本地 jj workspace 的 whole 项目连接可继续获取它已记录的原生状态。
来源根的 origin 保留历史名字；来源的 =origin#inner= 展平为外层项目内的 =origin@inner=。
remote 名含 =@= 时，revset 内也要引用它，例如：

#+begin_src sh
jjosh log -r 'main#inner#parser@"origin@inner"'
#+end_src

命令会报告映射。多个历史连接可以同名；发生歧义时，从 =bookmark list --all-remotes= 的输出选择明确物理身份，不要猜名字。
一旦创建当前逻辑 origin，它就优先于历史 origin，即使当前连接还没有第一次 fetch。

** 保留来源已有的多项目组织

如果来源已经有多个项目，且希望保留它们的身份和连接，用 preserve 而不是再包一层：

#+begin_src sh
source_change=$(jjosh --ignore-working-copy -R /path/to/team-work log -r @ --no-graph -T change_id)
jjosh project import --preserve team=/path/to/team-work --mount team=vendor/team
jjosh new @ "$source_change"
#+end_src

来源 parser 的 =libs/parser/= 变为 =vendor/team/libs/parser/=；项目、绑定、连接身份与稳定 label 不变。
=main#parser= 仍是该项目书签；来源根书签 =topic= 变为 =team/topic=。不会新建名为 team 的外层项目。
需要重命名的来源根 remote 物理名字使用 =team-原名=；项目 remote 按保留的连接身份定位。

与 nested 不同，preserve 保留当前项目逻辑连接及其本地 URL、push URL 和 remote 设置，也保留历史观察。
引用的本地存放位置按目标布局安排，服务器上的 ref 名和 push 目标不变。
不复制全局凭据，不在导入时访问网络；来源本来没有地址的连接仍离线。
已有配置的项目连接可以直接使用：

#+begin_src sh
jjosh git fetch --remote origin#parser
#+end_src

原生版本对应关系、隐藏转换锚点和过滤来源所需的原始对象、转换记录一起保留，后续转换不依赖原来源目录。
原 endpoint/ref 的发布 lease 也保留，包括旧 lease 和未跟踪分支的发布记录；缺失 lease 不等于已经观察到目标不存在。
修改地址不授予新目标的发布依据。

preserve 在提交目标操作前拒绝项目身份重复、布局不一致、名称/label/路径/引用冲突、未解决元数据或不兼容转换依据。
仓库级过滤绑定不能搬到挂载目录；有地址却未绑定项目的普通根 remote 也不能只靠复制 URL 继续挂载后的历史。这类来源应保持独立，或改用 nested。
依赖 URL rewrite、相对路径或 refspec 而无法在目标保持原意的配置会明确拒绝，不会静默连到另一个仓库。
同一项目的持续更新使用现有连接 fetch，而不是再次 import。

** 一次导入多个来源

两种模式可重复、可混用；至少一个来源，来源名字跨模式也必须唯一。
默认挂载在 =NAME/=，用 =--mount NAME=DEST= 覆盖：

#+begin_src sh
jjosh project import \
  --preserve team=/path/to/team-work --mount team=vendor/team \
  --nested parser=/path/to/parser-work --mount parser=libs/parser
#+end_src

这个例子要求 team 的已有项目不与新 parser 冲突。
所有来源一起规划、检查并在同一目标操作中发布，不会只发布部分来源。
两种模式都排除来源内置 =@git=：它是来源自己的 Git 同步记录，不是远端。
真实书签、tag 和开发图仍保留，目标的 =@git= 由目标自己的 Git 同步建立。

导入在安装前复核来源 operation 和 Git 配置，并以同一恢复日志安装配置及引用。
普通输入错误不会改目标配置和用户 refs，但已复制的不可变对象或完整来源对象库可能保留。
来源对象库在对象、浅边界和 refs 准备完成后才整体安装。
安装中断按本文“中断恢复”处理；不要手工删除来源对象库来重试。

* 连接不同的外部布局

同一项目可以同时配置 origin、upstream、fork、publish；每个连接都可 fetch 和 push。
创建绑定时确定项目与外部表示：

| 外部内容 | remote add 选项 |
|----------+-----------------|
| 整个仓库就是项目 | =--project parser --whole= |
| 项目位于 src/parser | =--project parser --filter ':/src/parser' --base main= |
| 各版本以 workspace.josh 定义布局 | =--project parser --view PATH= |
| 与现有连接采用相同表示 | =--like origin#parser= |

=--view PATH= 读取来源各版本中 PATH 目录下的 =workspace.josh=。
filter/view 反向发布需要外部上下文；=--base main= 指定来源分支，因此发布前要获取它。
=--like= 复用项目归属、表示和 base 规则，不复用地址或远端观察；若要不同 base，直接声明 filter/view 和 base。

建立 fork：

#+begin_src sh
jjosh git remote add fork /path/to/parser-fork.git --like origin#parser
#+end_src

如果已经创建了一个还没使用的普通根 remote，可以改为项目连接：

#+begin_src sh
jjosh git remote attach fork --project parser --whole
#+end_src

这是 remote add 的替代路径。attach 要求原连接没有绑定、获取记录或 tracking；保留连接身份，移入项目并释放根名字。
不同的 whole/filter/view 表示应有不同绑定或 remote；set-url 只改地址，不改表示。

** 名字、地址与生命周期

#+begin_src sh
jjosh git remote list --project parser
jjosh git remote rename --project parser fork publish
jjosh git remote set-url publish#parser /path/to/new-fork.git
jjosh git remote rename --project parser publish fork
#+end_src

rename 保留连接与绑定身份，也不改变项目连接的物理 Git handle。
项目连接的 handle 是 =jjosh-<ConnectionId>=；普通根 Git remote 仍用原来的物理名字。
日常命令用逻辑名字，不要编辑内部 Git 键来切换项目。

读取和发布地址默认相同。创建时可加 =--push-url URL=，以后分别修改：

#+begin_src sh
jjosh git remote set-url --project parser fork --fetch /path/to/read.git
jjosh git remote set-url --project parser fork --push /path/to/write.git
#+end_src

不再需要连接时，用 =jjosh git remote remove fork#parser=。
这也适用于没有本地地址的当前逻辑 remote：离线移除当前连接的引用、tracking 和相关元数据，不删本地项目内容，旧 operation 仍保留历史。
同名重新 add 创建的是新连接，不继承旧连接身份或 tracking。
恢复旧逻辑连接后的重新接线见“恢复操作”。

* 日常开发、tracking 与批量获取

应用和依赖可以同属一个 change，也可以拆成多个相互依赖的 change。
用 =status=、=diff= 检查，=describe= 写说明，=new= 开始新修改，=rebase=、=squash= 整理历史；这些沿用 [[file:../jj/docs/][jj 的日常用法]]。

#+begin_src sh
jjosh git fetch --project parser --remote origin --branch main
jjosh log -r '@ | main#parser@origin'
jjosh new @ main#parser@origin
#+end_src

fetch 更新观察，不替你选整合方案。上例 new 合并当前工作与新来源；也可以按修改图选择 rebase。
在同一个工作目录解决冲突，并构建、测试应用及依赖。

** 本地书签与跟踪

#+begin_src sh
jjosh bookmark create topic#parser -r @
jjosh bookmark track main#parser@origin
jjosh bookmark list --all-remotes
#+end_src

=topic#parser= 选定交付版本，以后可用 =bookmark set topic#parser -r REV= 移动。
=bookmark track= 让本地 main 在后续 fetch 时与该远端的更新合并移动；它不改变当前工作头。
默认新远端书签为 untracked；配置自动跟踪时例外。

** 每个项目独立选择默认连接

选择顺序：显式 =--remote= → =git.projects.LABEL.fetch/push= → 项目唯一连接 → 项目内 origin。
仍不唯一或配置无效就报错，不回退到根。
例如仍从 origin 获取，只向 fork 发布：

#+begin_src sh
jjosh config set --repo git.projects.parser.push fork
jjosh git fetch --project parser --branch main
#+end_src

配置支持名字、模式和列表，模式只匹配当前项目：

#+begin_src toml
[git.projects.parser]
fetch = ["origin", "fork"]
push = "fork"

[remotes."origin#parser"]
auto-track-bookmarks = "main"
#+end_src

配置段的 parser 是稳定 label；=fetch = "glob:up*"= 可选择该项目匹配的连接。
每个 remote 的 =fetch-bookmarks=、=fetch-tags= 和自动跟踪设置也用限定名。
=remotes.origin=、=git.fetch=、=git.push= 只影响根。
项目 rename/remove remote 会调整对应的仓库级默认值与限定设置；用户级配置须自行维护。这些本地配置不随 op restore 倒退。

** 一次接收多个项目

先为 app 等项目登记并配置连接，然后使用：

#+begin_src sh
jjosh git fetch --project parser --project app --branch main
jjosh git fetch --all-projects --branch main
jjosh git fetch --all-projects --all-remotes
#+end_src

重复 =--project= 会去重，它与 =--all-projects= 互斥；两者都不包含根。
=--all-projects= 选择未删除的登记项目，遇到冲突定义或没有活动连接的离线项目会报错，不会悄悄跳过。
=--all-remotes= 只在所选范围展开；无项目选择时只操作根，也可以明确写 =--remote origin#=。

每个项目分别解析显式 remote 名/模式与自己的默认值。
例如 =--project parser --project app --remote origin= 要求两者各有 origin，不能借用根或其他项目的连接。
整批先完成项目、配置、连接预检；任何一项无效都在首次网络请求前失败。
服务器不可达等后续网络错误仍可能留下部分获取结果，以各连接报告为准。

* 交付分支和版本

** 先看计划，再发布

为 parser 配置好 fork。目标已有分支时先获取目标状态，例如：

#+begin_src sh
jjosh git fetch --project parser --remote fork --branch main
#+end_src

若书签已经跟踪别的 remote，首次向 fork 发布前显式跟踪新目的地：

#+begin_src sh
jjosh bookmark track topic#parser@fork
#+end_src

写好待交付历史的说明，解决所选项目内的冲突并完成测试：

#+begin_src sh
jjosh git push --remote fork --bookmark topic#parser --dry-run
jjosh git push --remote fork --bookmark topic#parser
#+end_src

先检查 dry-run 输出再执行第二条：它列出实际地址、项目路径、表示、目标 ref 和前后 Git 对象 ID。
远端分支叫 =topic=；whole 将项目放到远端根，filter 示例则放回 =src/parser/=。
空目标上的 whole 绑定可首次 push；filter/view 必须有可用来源上下文，空目标不能提供 base 时使用一次性导出。

** 多项目发布

各项目都有对应交付书签时：

#+begin_src sh
jjosh git push --bookmark 'glob:topic#*' --dry-run
jjosh git push --remote fork --bookmark 'glob:topic#*' --dry-run
#+end_src

第一条按每个项目的默认值选择目标；第二条要求每个项目各有 fork。
=glob:= 显式启用模式，外层引号防止 shell 展开。
范围来自所选书签或 tag 的 label，不来自这个提交修改了哪些目录。
普通根引用使用根默认值；项目引用不继承根默认值。

所有目标先完成转换和预检，再开始传输；不同服务器间不能原子提交。
确认后去掉 =--dry-run=。部分传输失败时按各目标结果处理，不要把整批当作全未发布。

** tag 与删除

#+begin_src sh
jjosh tag set v1.0#parser -r topic#parser
jjosh git push --remote fork --tag v1.0#parser
#+end_src

远端 tag 叫 =v1.0=。支持轻量 tag 和未签名的 annotated commit tag；转换签名 tag 会拒绝。
tag 的不可变规则可能将工作副本移到新子提交。
移动已有 tag 使用 =tag set --allow-move=；删除用 =tag delete=，随后 push 对应 tag 删除。
获取远端 tag 后可用 =tag track= 跟踪。
分支同样先 =bookmark delete=，再按原目的地 push 对应书签的删除。

** 一次性导出到普通根 remote

origin#parser 已获取转换所需上下文，另有一个空 Git 仓库时：

#+begin_src sh
jjosh git remote add export /path/to/empty-parser.git
jjosh bookmark track topic#parser@export#
jjosh git push --remote export# --source origin#parser \
  --bookmark topic#parser --dry-run
#+end_src

检查后去掉 =--dry-run=。origin#parser 提供绑定及来源上下文，根 export 只提供发布地址。
=topic#parser@export#= 的末尾空范围明确选择根 remote。
长期双向同步应建立项目绑定；已经绑定的目标始终使用自己的表示，不能用 =--source= 替换它。
反向投影可用 =git push --base BRANCH= 明确本次来源上下文，=--merge= 将反向投影历史与来源上下文合并；它们不取消目标检查。

** 目标被别人更新了

push 校验实际 endpoint/ref 的精确 Git 对象 ID，称为发布 lease。
看到 stale lease，应获取*实际发布目标*，再决定整合还是重写。
annotated tag 即使只改注释，对象 ID 也会变化。
upstream、fork、镜像各有自己的依据；别处的观察、改 URL 或恢复旧 operation 都不能替目标授予发布许可，也不能绕过 lease 检查。

* 只选择需要的文件或历史

** 稀疏检出与工作目录映射

仅检出完整树中的 parser，再把它显示在工作目录根：

#+begin_src sh
jjosh sparse set root:libs/parser
jjosh sparse map set libs/parser=.
#+end_src

前者选文件，后者改工作副本中的位置；编辑仍记录到提交的 =libs/parser/=，不改项目或 remote 的外部表示。
路径映射要求非 colocated 工作树；=sparse map set= 一次替换整组映射，坐标相对 workspace 根。
=sparse map list= 查看映射，=sparse map reset= 恢复原位置，=sparse reset= 恢复完整检出。
多目录选择见 [[file:../jj/docs/filesets.md][filesets 文档]]。

** 浅获取、指定对象与临时镜像

Git filter/view 来源首次 fetch 可加 =--depth 1=，以后加深：

#+begin_src sh
jjosh --config git.abandon-unreachable-commits=false \
  git fetch --project parser --remote origin --branch main --deepen 50
#+end_src

用 =--unshallow= 替换 =--deepen 50= 补全历史；不能对非浅来源直接 deepen。
上面的配置保留旧浅边界版本，供随后显式整合；当前自动放弃旧边界并重写本地后继的路径可能触发 root merge 错误。
浅边界按来源地址隔离；发布缺祖先时可能需要补全。普通连接和本地 jj 原生来源使用完整获取。

获取来源完整 commit ID，或临时改用镜像：

#+begin_src sh
jjosh git fetch --project parser --remote origin --revision OID
jjosh git fetch --project parser --remote origin --branch main \
  --fetch-url /path/to/parser-mirror.git
#+end_src

=--revision= 可重复，不自动获取默认分支/tag，与 =--tracked= 互斥，且要求服务器允许获取该对象。
使用输出 =Fetched revision RAW as CANONICAL= 中的 CANONICAL 选择本地版本；本地 jj 原生来源不支持 raw OID 选择。
=--revision= 和 =--fetch-url= 都要求整批去重后恰好一个物理 named remote，多个项目里同名 origin 不算一个。
镜像只影响本次获取，不改发布地址，也不替实际发布目标提供 lease。

** 仓库级过滤与预览

在另一个目标仓库，不指定项目即可让过滤结果成为整个仓库根：

#+begin_src sh
jjosh git remote add upstream /path/to/components.git --filter ':/src/parser'
jjosh git fetch --remote upstream --branch main
jjosh new main@upstream
#+end_src

也可以用 =--view PATH=；发布仍用 git push。不要把这种仓库级绑定与项目目录或 sparse 映射混为一谈。
仅查看当前仓库某个已记录版本的过滤结果：

#+begin_src sh
jjosh projection preview ':/libs/parser' -r @ --files --history
#+end_src

可加 =--json=，或用 =--view PATH= 替换 filter。preview 不改变记录状态；具体 remote 的交付结果仍用 push dry-run 检查。

* 恢复操作，而不是倒退服务器

先用 =jjosh op log= 找到 OP，再用 =jjosh --at-op OP log= 查看当时的修改图。
restore 创建一个新 operation，不删除后来操作，也不撤销已经发生的外部发布。

| 选择 | 恢复的内容 | 保持当前的内容 |
|------+------------+----------------|
| =op restore OP --what repo= | 修改图、本地引用、workspace 记录与布局；项目、绑定、label、逻辑 remote 名与连接归属 | 历史远端观察与 tracking |
| =op restore OP --what remote-tracking= | 远端引用、tracking、转换观察及观察当时的连接身份/名字 | 当前项目、绑定、逻辑名字和连接归属；本地引用 |
| =op restore OP= | 上述两部分一起恢复 | 下述本地传输状态及外部世界 |

所有选择都*不倒退*实际 URL、认证、本地默认配置、当前 Git mirror 同步基线、endpoint/ref 发布 lease 或服务器状态。
所以恢复了一个名字，不代表恢复了当时的联网配置。
同一连接只是 rename 时，观察按连接身份跟随当前名字；普通根 remote 改名或互换名字后，只恢复 tracking 也不会把当前名字改回去。

** 删除后同名重建：当前名字不让位给历史

把旧连接称为 A，删除后同名新建的称为 B。
只恢复 A 时代的 remote-tracking，不会把当前 origin 改回 A；即使 B 尚未首次 fetch，origin 仍选择 B，之后 fetch 使用 B 的表示和独立 tracking。
不需要用 project resolve 修补名字，也没有独立的公开“忘记观察”命令。

旧历史仍可明确查看：

#+begin_src sh
jjosh bookmark list --all-remotes
#+end_src

照抄列表给出的物理选择器。例如旧项目连接可能显示 =main#parser@jjosh-<旧ConnectionId>=；根的旧 origin 观察会归档为 =main@jjosh-observed-<旧ConnectionId>=。
将其中身份替换为实际输出后用于 =jjosh log -r '完整引用'=。
旧根观察不会覆盖 B 的 refs 或 tracking。读取历史范围不要求重新激活当时的项目或绑定。

** 完整恢复后离线移除或重新接线

完整恢复可能恢复逻辑 A，但 A 的本地配置早已删除。
查看项目定义与本地配置：

#+begin_src sh
jjosh project show parser
jjosh git remote list --project parser
#+end_src

若还要 A，显式提供地址重新连接；这保留 A 的连接身份与绑定：

#+begin_src sh
jjosh git remote set-url origin#parser /path/to/parser.git
#+end_src

随后正常 fetch。若不再需要 A，直接 =jjosh git remote remove origin#parser= 即可离线移除。
不会借用同名 B 或其他项目的配置。
普通根 remote 若同一个物理配置已属于 B，重新连接 A 会拒绝覆盖；按诊断明确处理该配置的保留、改名或移除，再重新接线。
set-url 不是更换 whole/filter/view 的方式；需要不同表示时有意建立新的绑定/remote。

* 项目维护、迁移与故障恢复

** 检查与调整项目

#+begin_src sh
jjosh project list
jjosh project show parser
jjosh project check parser
#+end_src

这些命令离线工作并支持 =--json=；无参数 =project check= 检查全仓库。
=project rename parser syntax= 只改显示名，书签仍用 =#parser=；当前没有目录与 label 整体迁移的专用命令。
停止维护项目时，先处理绑定、引用和 tracking，再 =project remove NAME=；文件和提交不删除。

仅在真实元数据冲突时使用 project resolve，按 list/show 的 ID 和候选编号处理：
=--id ID --candidate N= 选项目定义，=--id ID --name NAME= 解决显示名；
=--binding ID= 或 =--label LABEL= 配合 =--candidate N= 选择绑定/label；=--delete= 删除所选定义，须先处理依赖。
逻辑 remote 名冲突用 =--connection ID --candidate N= 或 =--connection ID --name NAME=，不能借改名跨项目迁移。
=project resolve --binding ID --delete= 也可停用已断开且无依赖的旧绑定。这些不是 tracking-only restore 的必做步骤。

** 中断恢复

remote 修改、原生 import 或迁移若报告未完成的本地安装，按报错选择：

| 命令 | 使用条件与效果 |
|------+----------------|
| =jjosh git remote recover --rollback= | 原 operation 上恢复日志保存的旧本地配置和 refs，再重试 |
| =jjosh git remote recover --accept= | 已提交状态经一致性校验后，保留修改并完成收尾 |

恢复不访问网络。外部配置/ref 已有不兼容修改时，先处理诊断，不能盲目 accept。
仍被使用的 Git 锁文件应由对应进程释放。

** 升级旧仓库

备份仓库元数据*和来源对象库*；停止不兼容的 jj 程序及原生 Git 并发写者，然后查看计划：

#+begin_src sh
jjosh project migrate --dry-run
#+end_src

不带选项也只显示计划。当前项目存储格式是 =simple_op_store_projects_v3=，包含历史连接身份记录。
v1/v2 仍可读，但写入前必须显式执行 =project migrate --apply --exclusive=；不会自动允许旧 writer。
旧 operation 继续按其记录的身份读取。即使没有登记子项目，通过 jjosh 创建或管理普通根 remote 也会记录连接身份，并可能选择 v3 存储。
普通根的物理 Git 名字仍可为 origin，不代表仓库可由旧版或上游原版 jj 写入；这些 writer 不得写入 v3 存储。

计划列出项目目录、表示、名字、内部连接重定位、引用处理及退役元数据。
旧别名逐字保留，例如 parser-upstream 成为项目内同名 remote，不自动去项目前缀；项目 handle 改用独立身份，而不是改变连接/绑定身份。
迁移后可以 =git remote rename --project parser parser-upstream origin= 简化名字。
仓库级 =remotes.NAME= 移到限定名；旧 =remote.NAME.jjosh-readOnly= 清理。
用于选择项目连接的根 =git.fetch/git.push= 应改成 =git.projects.LABEL.fetch/push=。

按诊断补充明确选择：

| 选项 | 用途 |
|------+------|
| =--representation REMOTE=whole= | 整个来源就是项目 |
| =--representation REMOTE=filter:EXPR= | 项目挂载前的来源 filter |
| =--representation REMOTE=view:PATH= | 来源版本化 view |
| =--native-source PROJECT=REMOTE= | 原生对应关系归入同项目 whole 绑定 |
| =--native-source PROJECT=detached= | 保留离线原生对应关系，默认选择 |
| =--clear-observations REMOTE= | 可选地清除旧远端记录、tracking 和 canonical mirror；不是迁移前提 |

例如确认旧 parser-upstream 的布局后：

#+begin_src sh
jjosh project migrate --dry-run \
  --representation 'parser-upstream=filter::/src/parser'
jjosh project migrate --apply --exclusive \
  --representation 'parser-upstream=filter::/src/parser'
jjosh project check
#+end_src

迁移可离线完成，不要求重新 fetch。默认保留旧观察、tracking 和 canonical mirror，也保留本地引用、工作文件、来源对象、浅边界、发布 lease 和有效连接配置。
保留缓存不补造缺失的转换依据或发布 lease，也不证明远端当前状态。
include/global remote 设置、孤立旧附属元数据和配置冲突需按诊断先整理，不能静默覆盖。
从计划到 apply 完成应一直保持维护窗口；=--exclusive= 是已停止不兼容写者的确认，不是全局 Git 锁。
日志建立前的并发写入不受恢复校验保护；安装中断按前面的 recover 处理。

** 数据与权限边界

历史转换要求 SHA-1 Git backend；gitlink 作为引用保留，不递归展开。
来源对象和转换锚点可能仍被历史操作需要；删除来源对象库或对它做 GC 是可能不可逆的数据删除，不是普通“清缓存”。
先备份并确认历史转换与恢复依赖，不能把重新 fetch 当作总能补回全部原生状态的保证。
原生 Git 直接与外部仓库通信，过滤不是访问控制；服务器负责认证与授权。
