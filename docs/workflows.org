#+title: jjosh 工作流
#+options: toc:2 num:nil

按当前要做的事选择一节，不需要从头依次执行。
命令默认在目标仓库根目录运行；构建和创建仓库见 [[file:../README.org][README]]。

示例使用项目 =lib=、目录 =packages/lib/=、来源分支 =main=。
=lib-upstream= 用于接收上游，=lib-origin= 用于向自己的 fork 发布；名字没有特殊含义。
把示例地址换成实际仓库地址，分支名也以来源为准。

* 接入项目

根据项目当前在哪里，选择一种方式。同一项目不需要重复接入。

** 来源是 Git 仓库

假设要把来源的 =src/= 放到 =packages/lib/=：

#+begin_src sh
jjosh projection remote add lib-upstream /path/to/lib.git ':/src' \
  --project lib --mount packages/lib --base main --read-only
jjosh git fetch --remote lib-upstream --branch main
jjosh new @ main#lib@lib-upstream
#+end_src

filter 选择来源内容，mount 决定它在本仓库的位置。要接入整个来源，使用 =':/'=。
=--base main= 指定反向转换的来源上下文；实际获取哪些引用仍由 fetch 选择。

这里用 =new= 把当前工作与来源合在一起。若目标还是空仓库，也可以直接 =new main#lib@lib-upstream=，从来源开始工作。
只需当前版本、不需要完整来源历史时，在首次 fetch 加 =--depth 1=；后续仍使用同一个 remote。

** 来源是正在开发的 jj 仓库

先在来源仓库运行 =jjosh status=，记录要带走的工作文件。然后回到目标仓库：

#+begin_src sh
jjosh native import --source lib=/path/to/lib-work --mount lib=packages/lib
jjosh new @ workspace/default#lib
#+end_src

=default= 是来源 workspace 名。import 保留已记录的原生版本、change ID、分叉和冲突，不复制旧 operation history。
已有本地工作用上面的 =new @ …= 组合；空目标可以直接 =new workspace/default#lib=。

为已导入项目登记持续获取的来源，不再重复 import：

#+begin_src sh
jjosh git remote add lib-upstream /path/to/lib-work
jjosh projection remote attach lib-upstream lib --read-only
#+end_src

来源可以是本地 jj workspace，也可以是与该项目对应的 Git 仓库。attach 保持已有 native 转换，不重新导入内容。

** 目录已经在当前仓库里

只需把已记录的目录登记成项目：

#+begin_src sh
jjosh status
jjosh projection add lib --mount packages/lib
#+end_src

这不移动文件，也不要求先有 upstream。接下来配置发布地址即可。

* 接收上游更新

项目已接入且来源已配置时，日常只需要获取所需分支：

#+begin_src sh
jjosh git fetch --remote lib-upstream --branch main
jjosh log -r '@ | main#lib@lib-upstream'
#+end_src

=main#lib@lib-upstream= 是来源 main 的观察，不是当前工作头。
确认要接收这个版本后，再决定如何整合。例如保留当前工作，并把上游作为另一个父提交：

#+begin_src sh
jjosh new @ main#lib@lib-upstream
#+end_src

也可以按自己的修改图选择 rebase 或 squash。fetch 不替你选择这种策略；jj 的 tracking 和不可达提交处理规则仍然适用。
整合产生冲突时先解决冲突，不要直接发布所选项目的冲突版本。

若希望本地 =main#lib= 跟踪这个来源，显式执行 =jjosh bookmark track main#lib@lib-upstream=。
跟踪负责引用更新，不等于把工作副本切换到该分支。

* 向自己的 fork 发布

先在托管平台或本地创建目标 Git 仓库，再配置一次发布 remote。按项目的接入方式选择配置：

** Git 过滤项目

fork 也需要用于 fetch 时，为它配置与 upstream 相同的来源 filter：

#+begin_src sh
jjosh projection remote add lib-origin /path/to/lib-fork.git ':/src' \
  --project lib --mount packages/lib --base main --writable
#+end_src

不要用普通 remote 的 attach 代替这一步：attach 不会复制另一个 remote 的 filter。

** Native 项目或本仓库已有目录

#+begin_src sh
jjosh git remote add lib-origin /path/to/lib-fork.git
jjosh projection remote attach lib-origin lib --writable
#+end_src

** 选择并发布修改

如果 fork 已有 main，先用 =jjosh git fetch --remote lib-origin --branch main= 获取它的状态。
空仓库跳过这一步。发布其他已有分支时，获取那个分支，而不是用 upstream 的观察代替目标观察。

整理待发布的修改，并为待发布历史中的提交写好说明，不只是当前提交。下面以 =@= 为发布终点，新建一个 topic 书签：

#+begin_src sh
jjosh bookmark create topic#lib -r @
jjosh git push --remote lib-origin --bookmark topic#lib --dry-run
#+end_src

确认目的地和引用动作后发布：

#+begin_src sh
jjosh git push --remote lib-origin --bookmark topic#lib
#+end_src

已有 =topic#lib= 时，用 =bookmark set topic#lib -r @= 移动它，不重复 create。
远端分支叫 =topic=；Git 过滤项目的文件映射回来源路径。其他项目的修改留在本地，不必为了单独发布而拆开整合提交。

再次获取自己发布的分支仍用 =git fetch --remote lib-origin --branch topic=。
不要假定有损转换后的版本一定具有原 commit ID，也不要把相同 change ID 当成整份提交等价的证明。

* 同时交付多个项目

先为每个项目选择发布终点。多个书签可以指向同一个整合提交，也可以指向不同版本。

没有显式 =--remote= 或 =git.push= 配置时，以下命令按每个项目的唯一可写绑定分别发布：

#+begin_src sh
jjosh git push --bookmark 'topic#*' --dry-run
#+end_src

检查计划后去掉 =--dry-run=。引用模式需要引号，避免 shell 展开。
有多个可写候选时逐个明确选择 remote；命令不会根据提交改了哪些目录猜发布对象。
多个 remote 不是原子事务，发生部分失败时要分别处理已经成功与尚未成功的目标。

* 发布版本号

选择已准备好的具体版本创建 tag，例如已发布的 =topic#lib=：

#+begin_src sh
jjosh tag set v1.0#lib -r topic#lib
jjosh git push --remote lib-origin --tag v1.0#lib
#+end_src

远端 tag 叫 =v1.0=。创建 tag 可能使目标不可变，并让当前工作副本移到新子提交。
移动已有 tag 要显式使用 =tag set --allow-move=；删除则先 =tag delete=，再发布该 tag 的删除。

轻量与 unsigned annotated commit tag 支持转换。签名 tag 的转换会拒绝；annotation-only 的远端变更也会触发 stale lease。
获取 tag 不会自动把它变成本地 tag，需要时显式 =tag track=。

* 调整浅历史的深度

前提是这个 Git projection 来源已通过 =--depth= 浅获取。普通后续 fetch 不会自动补齐旧历史。

再获取一段祖先历史：

#+begin_src sh
jjosh --config git.abandon-unreachable-commits=false \
  git fetch --remote lib-upstream --branch main --deepen 50
#+end_src

或者补全来源能提供的历史：

#+begin_src sh
jjosh --config git.abandon-unreachable-commits=false \
  git fetch --remote lib-upstream --branch main --unshallow
#+end_src

这两个操作按需选择，不必连续执行。若 deepen 已补齐全部历史，就不再 unshallow。

*现有限制：* 深化会改变转换后的父图。默认自动放弃旧边界版本可能重写本地后继并触发 root merge 错误。
上面的配置保留旧版本，之后由你显式整合新的来源观察；这项底层问题尚未修复。

浅历史只适用于 Git projection，不适用于 native JJ 导入。
浅边界按来源 endpoint 隔离，不把 monorepo 标成 shallow。向缺少共同祖先对象的目标发布时，可能需要先补全历史。

* 获取指定版本或改用镜像

已知完整的来源 commit ID 时，用 =jjosh git fetch --remote lib-upstream --revision OID=，将 =OID= 替换为该 ID。
命令输出 =Fetched revision RAW as CANONICAL=，其中 =CANONICAL= 才是本地 revision 操作使用的 ID；这次获取不会创建 remote bookmark，也不会顺带获取默认分支/tag。
=--revision= 可重复，但不能与 =--tracked= 合用；服务器必须允许请求该对象。

临时改从镜像获取，不修改已配置的 remote 地址：

#+begin_src sh
jjosh git fetch --remote lib-upstream --branch main --fetch-url /path/to/lib-mirror.git
#+end_src

这两个选项都要求恰好选中一个 named remote。直接读取本地 jj workspace 的 native 路径不支持 raw OID 选择。
镜像提供转换输入，不授权覆盖另一个 endpoint 上的引用。

* 让项目在工作副本根目录构建

如果完整提交里已有 =packages/lib/=，只想把它检出到根目录，不需要重新导入或建立另一份历史。
在非 colocated 工作树中执行：

#+begin_src sh
jjosh sparse set root:packages/lib
jjosh sparse map set packages/lib=.
#+end_src

之后直接在工作副本根目录编辑、构建。修改仍记录在 canonical 的 =packages/lib/= 下，未检出的内容保留。
要恢复全量布局，执行 =jjosh sparse reset=；只重置映射用 =jjosh sparse map reset=。
多目录映射与中断恢复见 [[file:../jj/docs/filesets.md][filesets 文档]]。

* 遇到问题时

- *不知道项目绑定了什么*：用 =projection list=、=projection show lib=、=projection check=。它们不连接远端。
- *不确定要发布什么*：用 =projection preview --project lib -r REV --files --history= 看本地视图，再用 =git push --dry-run= 看实际目的地和引用动作。
- *目标已经变化*：重新 fetch 实际发布目标，再决定如何整合或重写。没有绕过精确 lease 的 =--force=。
- *需要撤销本地操作*：=op restore= 不撤销外部发布，也不回滚发布记录。
- *删除了 remote，想重新接上*：项目挂载仍在，重新配置 remote 即可，不需要再次导入源码。

私有来源对象与转换对应关系可能是后续逆转换的必要输入；不要只备份工作文件，也不要把这些记录当临时缓存删除。
