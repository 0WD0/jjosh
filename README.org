#+title: jjosh
#+subtitle: 一张修改图，一起开发，分别送回上游
#+options: toc:nil num:nil

jjosh 把 jj 的原生修改管理和 Josh 的历史转换放到同一个命令里。这里要保留的是各个项目正在进行的开发，而不只是把几份源码拼到一个目录下：未发布的 change、分叉、合并和冲突都应有自己的位置。

日常仍然用 jj 的 new、rebase、squash 整理修改。jjosh 负责把来源历史接进来，以及把选定项目的修改送回去。/获取、整合、发布是三件独立的事。/

* 先继续开发这个仓库

代码就在四个地方：

- [[file:jj/][jj/]]：jj 本地分支，包含原生状态和 sparse 工作副本的改动。
- [[file:josh/][josh/]]：Josh 本地分支，负责过滤、投影与反向历史映射。
- [[file:gitoxide/][gitoxide/]]：gitoxide 上游源码，提供 Git 对象、引用和协议层。
- [[file:crates/jjosh-cli/src/][crates/jjosh-cli/]]：把 jj、Josh 和 gitoxide 接起来的 CLI、native 导入和来源管理。

在仓库根构建；当前 workspace 要求 Rust 1.95+，运行时需要 Git：

#+begin_src sh
cargo build --locked --release -p jjosh-cli
export PATH="$PWD/target/release:$PATH"
export JOSH_EXPERIMENTAL_FEATURES=1
#+end_src

三个上游子目录保留各自的 Cargo workspace。根 =.cargo/config.toml= 将 jj、Josh 与根 workspace 的 gitoxide 依赖统一接到 =gitoxide/= 本地源码；相关 manifest 与 lockfile 一起维护。

日常同步由 named Git remote 决定，不从 =.link.josh= 推断当前 URL 或发布目标。先查看实际配置，再选择来源；以下名字和分支仅为示例：

#+begin_src sh
jjosh git remote list
jjosh git fetch --remote jj-upstream --branch main
jjosh git fetch --remote josh-upstream --branch master
jjosh new @ main#jj@jj-upstream master#josh@josh-upstream
#+end_src

这里的 =new= 是一种整合选择，不是 fetch 的副作用。也可以只整合一个项目，或按当前修改图用 rebase/squash 接续。

发布到已配置的 fork 时，创建或移动 bookmark 与 push 分开执行：

#+begin_src sh
jjosh bookmark create topic#jj -r @
jjosh bookmark create topic#josh -r @
jjosh git push --remote jj-origin --bookmark topic#jj
jjosh git push --remote josh-origin --bookmark topic#josh
#+end_src

push 沿用 jj 的选择和 tracking，根据选中引用的 =#scope= 自动导出对应项目，并把 =topic#jj= 发布为源坐标的 =topic=。
发布 remote 只决定 endpoint，不必附着到项目；缺失 scope 转换规则或多个引用映射到同一个远端名字时会拒绝发布。

* 几种能力，别混成一件事

| 想做的事 | 用什么 | 改变什么 |
|----------+--------+----------|
| 把已有 jj 项目的开发状态纳入 monorepo | native import | 将来源原生图映射到目标目录，保留 change 身份 |
| 持续获取、发布一个子项目 | git fetch/push | 来源坐标与 monorepo 坐标之间的历史和普通 jj 远端观察 |
| 只检出一部分文件，或换一种本地构建布局 | sparse | 工作副本，不生成另一份提交历史 |
| 把仓库的一部分作为独立历史视图开发 | projection | 经过 Josh 转换的历史，可反向发布 |
| 在仓库内整体搬迁一段可变修改图 | native transplant | 显式选定提交的路径与父关系 |

native 与 link 可以配合：先把已有本地软 fork 原样纳入，再用 link add 初始化 named remote。也可以把普通 Git remote 通过 =projection remote attach= 绑定到项目。不必把当前 fork 顶端伪装成一个干净上游基线。

* 把已有项目接进来

** 保留正在进行的 jj 开发

来源先记录要带走的工作文件；import 本身只读取来源已记录的状态。以下以 Ebox 和 Ekp 为例，来源 workspace 名为 default：

#+begin_src sh
jjosh -R /path/to/ebox status
jjosh -R /path/to/ekp status

jjosh git init --no-colocate --object-hash sha1 combined
jjosh -R combined native import \
  --source ebox=/path/to/ebox \
  --source ekp=/path/to/ekp
jjosh -R combined new @ workspace/default#ebox workspace/default#ekp
#+end_src

已有目标仓库可以直接 import，不需要重新 init。每个 NAME 是当前实现中的 canonical 顶层目录和引用前缀，允许 ASCII 字母、数字、=-=、=_=；占用的目录或命名空间会被拒绝。

导入保留选定当前 view 及其所需父历史：change ID、空提交、有序 merge 父边、当前 divergence、原生冲突树和冲突引用。目录与父 ID 映射会改变 commit ID；失效的提交签名会移除并报告。/不搬迁旧 operation/evolution 历史，也不包含未记录的磁盘修改。/

源书签和 tag 默认叫 =原名#NAME=，remote 观察叫 =原名#NAME@NAME-原远端=。=workspace/default#NAME= 是导入时保留工作入口的普通书签，不是另一个已挂载 workspace。新建 native 实验仓库也可选择 [[file:docs/scoped-reference-convention-demo.org][=原名#NAME= 命名约定 demo]]；这不改变 jj 的引用模型。

** 接收上游，也接收外部贡献

native 的获取来源和发布目标不绑定。可以从 Git 上游、贡献者 fork 或本地其他 repo 的 jj workspace 接收指定分支：

#+begin_src sh
jjosh -R combined git remote add ebox-contributor /path/to/other-jj-workspace
jjosh -R combined projection remote attach ebox-contributor ebox
jjosh -R combined git fetch --remote ebox-contributor --branch topic
jjosh -R combined new @ topic#ebox@ebox-contributor

jjosh -R combined git remote add ebox-origin /path/to/ebox-fork.git
jjosh -R combined bookmark create review#ebox -r @
jjosh -R combined git push --remote ebox-origin --bookmark review#ebox
#+end_src

=--remote= 选择已配置的 named remote，不是临时 URL。fetch 将结果记为普通 remote bookmark；未跟踪的观察不改本地书签，显式 track 后沿用 jj 的引用合并规则。它不替你选择工作头，也不自动消除 divergence。本地 =.jj= 来源读取已记录的原生状态；普通 Git endpoint 通过 gitoxide 接收对象后转换。

push 只导出 Ebox 的内容，裁剪对该项目没有变化的提交，不拆分本地 canonical 修改图。已知源边界与发布对应关系会被复用；再次收到自己发布的版本时，可以接回对应的 canonical change。所选项目在发布终点的未解决冲突会阻止发布，其他项目的冲突不阻止它。

无法直接读取来源时，可以用 =native export FILE=、=native inspect FILE= 和 =native import --source NAME=FILE= 运输当前原生状态。Bundle 不是整个仓库的备份，也不携带来源内部项目的私有转换记录或发布 lease。

* 用 link 初始化项目同步

=link add= 初始化真实 Git remote、项目挂载和转换规则，并保留初始 raw pin 与 =PATH/.link.josh= 接入记录。项目名默认取 =PATH= 的末段（可由 =--name= 覆盖）；默认 remote 名为 =项目名-upstream=，因此来源的 =main= 会成为普通 jj remote bookmark =main#项目名@项目名-upstream=。它既可引入新来源，也可为有共同历史的原生导入项目登记来源；已占用项目不会被重做成源码快照。后续同步不读取 marker 中的 URL、target 或 push 字段。

#+begin_src sh
jjosh link add ebox /path/to/ebox.git \
  --target main \
  --push-url /path/to/ebox-fork.git

jjosh git fetch --remote ebox-upstream --branch main
jjosh new @ main#ebox@ebox-upstream
jjosh bookmark create topic#ebox -r @
jjosh git push --remote ebox-upstream --bookmark topic#ebox
#+end_src

默认 =embedded= 模式接入来源历史；=--mode snapshot= 用于快照式引入。新来源只需一部分内容时，可以在 URL 后加 Josh filter，例如 =':/src'=。关联已有原生项目则保持原挂载布局，不借此隐式改变 filter。

=git fetch= 不更新 marker 的 pin，不建立 =jjosh/trunk=，也不主动 merge/rebase。引用选择沿用 jj：

- 不给 =--branch= / =--tag=：按 named remote 的默认 fetch 选择和 jj 的 tag 规则获取。
- 显式选项可重复，支持 jj 名字模式和 =--tracked=。
- 只更新选中引用，包括匹配的来源删除；未选择的观察保留。

同一来源引用未变化时，重复 fetch 保持其投影后的 bookmark target。若来源回到刚由本地发布的版本，提交带有效 =jj:change-id= header 且投影内容相同，fetch 会复用本地已发布 commit；随后来源后继会接在该 canonical 父边之后，避免仅因发布再取回而产生重复版本。相同 change ID 但投影内容不同仍按 jj 的 divergence 规则保留，不会为回环强行合并。

没有有效 =jj:change-id= header 的 Git 提交会按 Git OID 合成 change ID。过滤或重写会改变 OID，因此设置 =git.write-change-id-header=false= 时，不保证取回后仍复用原本的本地 commit；这是 Josh 有损历史的边界，不应把它当作 round-trip 身份保证。

=git push= 按选中引用的 =#scope= 找到项目挂载和源历史转换，反向映射所选目录，并裁剪整段导出历史中对该项目没有内容变化的提交；描述不会使空提交绕过裁剪。link add 未指定 =--push-url= 时将该来源 remote 标为只读，发布可另配普通 writable remote。转换路径按实际 endpoint 与目标分支记录 raw 位置，后续重写使用精确 expected-old lease；失败或 =--dry-run= 不推进发布记录，没有绕过保护的 =--force= 入口。

* 一份 canonical 树，多种构建布局

如果目的只是让应用在工作副本根构建、共享依赖出现在它期待的位置，用 sparse，不必先制造投影历史。

假设完整提交中已经有 =src/Sunshine=、=src/moonlight-common-c= 和 =src/msquic=：

#+begin_src sh
jjosh sparse set root:src/Sunshine root:src/moonlight-common-c root:src/msquic
jjosh sparse set \
  --remove root:src/Sunshine/third-party/moonlight-common-c \
  --remove root:src/Sunshine/third-party/msquic \
  --remove root-file:src/Sunshine/third-party
jjosh sparse map set \
  src/Sunshine=. \
  src/moonlight-common-c=third-party/moonlight-common-c \
  src/msquic=third-party/msquic
#+end_src

这样在物理 =third-party/msquic/= 中编辑、新建文件，普通 snapshot 会写回 canonical =src/msquic/=。未检出的内容和冲突仍在完整提交里，revision 操作也不局限于可见文件。

选择与映射分开管理：

#+begin_src sh
jjosh sparse list
jjosh sparse edit
jjosh sparse map reset
jjosh sparse reset
#+end_src

=map set= 替换全部映射；存在显式映射时，映射范围之外的源不会检出。=map reset= 只恢复 identity 映射，=sparse reset= 同时恢复全量选择。普通路径参数使用物理坐标，=root:= / =root-file:= / =root-glob:= 明确使用 canonical 坐标；编辑器内容始终使用 canonical 坐标。

每个可写路径都必须有唯一归属，包括未来新建的文件，因此重叠映射可能被拒绝。上例的 =root-file:= 排除防止应用中的同名文件占用共享依赖的父目录，不排除整个 third-party 子树。

选择与布局记录在 operation 中，每个 workspace 各自持有配置，可以 undo/restore。非 identity 映射不能用于 colocated Git 工作树。详细规则及中断恢复见 [[file:jj/docs/filesets.md][filesets 文档]]；磁盘出现 =sparse-update-in-progress= 时，不要删标记后强行 snapshot。

* 需要独立历史时，再用 projection

projection 让局部视图成为一个可独立开发、再反向发布的仓库。这与 sparse 只改变工作副本不同：

#+begin_src sh
jjosh git init --no-colocate --object-hash sha1 api-view
jjosh -R api-view projection remote add mono /path/to/monorepo.git ':/services/api'
jjosh -R api-view git fetch --remote mono --branch main
jjosh -R api-view bookmark track main@mono
jjosh -R api-view new main@mono

# 在 api-view 中修改并整理提交后，明确选择发布终点。
jjosh -R api-view bookmark set main -r @
jjosh -R api-view git push --remote mono --bookmark main
#+end_src

也可以用 =--view src/Sunshine= 替代 filter，读取源仓库该目录的 =workspace.josh=。例如共享依赖定义：

#+begin_example
third-party/moonlight-common-c = :/src/moonlight-common-c
third-party/msquic = :/src/msquic
#+end_example

视图中的修改反向落到对应 canonical 源路径；它不是符号链接或实时共享目录，也不自动清理原路径重叠的 gitlink、重复文件和构建脚本。

发布选择沿用 jj 的 bookmark/tag 规则；=--base= 和 =--merge= 为 Josh 反向映射指定来源上下文。改变映射后，Josh 可能规范化定义、补入内容和调整父关系；重新 fetch 回来的版本可能保留 change ID，却有不同 commit ID。接续它时迁移尚未发布的后继，不要再次重放已经发布的映射提交。

投影 fetch 可选择分支和指向提交的 tags；反向发布转换后的 tags 尚不支持。获取不要求来源提供 HEAD 默认分支。Josh 不能保真转换含未解决 jj 原生冲突的所选祖先历史；需要保留这种状态时使用 native，而不是假定干净的 tip 能掩盖冲突祖先。

Git config 保存唯一真实 fetch/push 地址，Josh remote 文件只保存 filter 和语义元数据。没有本地 namespace façade，也不会再从自己 fetch 一次。旧的含 URL/refspec metadata 的 Josh remote 文件需要通过 =projection remote add= 显式重新配置；配置错误不会静默按普通 Git 处理。

* 真正需要记住的边界

- *历史坐标不等于引用名字。* =main#jj@jj-upstream= 仍是普通 jj 引用。fetch 根据来源配置转换，push 根据选中引用的 =#scope= 导出项目；直接运行原生 =git fetch/push= 会绕过它并连接真实上游，不是受支持的投影同步路径。
- *观察不是覆盖授权。* native/Josh 按实际目标 endpoint 与分支记录 raw lease；首次只允许创建或可证明的快进，已有观察时校验 expected-old。普通 Git 路径使用 jj 准备的引用 lease。收到新的 push advertisement 不自动刷新覆盖授权，未确认或结果不明的引用不按成功记账。
- *恢复本地操作不撤销发布。* =op restore= 不回滚远端或私有发布记录。非 colocated 仓库恢复引用后，先用 =jjosh git export= 同步物理 refs，再做 import。多个来源之间没有原子发布。
- *私有对应关系不是可随手删的缓存。* =refs/jjosh/native/NAME/= 同时保存转换边界并保活 raw/canonical 对象。旧 =jjosh-native-NAME= 伪远端用 =native migrate= 迁移，不手工改名或删除。
- *格式升级不是开关。* sparse 的新工作副本和 operation-store 格式会拒绝旧二进制，reset 不降级。切换前退出旧 jj 进程；更早的 =simple_op_store_native_remotes=、=simple_op_store_sparse= 实验格式不能靠改类型标记升级。
- *来源仍有外部边界。* 普通 Git 路径支持 SHA-1/SHA-256；native/Josh 转换仍只支持 SHA-1 Git backend。gitlink 不递归展开，缺失历史要先补齐。projection 会获取原始历史，不是权限隔离。网络对象传输使用 gitoxide；本地 native 对象搬运仍有 Git pack plumbing。

=native transplant= 留给另一类任务：在当前仓库内，通过 =--map= 和 =--parent= 整体重定位显式选定的可变修改图。它保留 change 身份与空提交，不跨仓库取对象，也不自动重定位 link metadata。选集必须闭合于受影响后代，外部父边需要明确映射；它不是普通来源同步或给引用增加 scope 的替代办法。
